## 1. 사업자 모델 결정표 (회신 오면 이 표대로 분기)

| Q1 다중 발신프로필 | Q4 타 사업자 채널 연결 | Q3 재판매·재청구 | → 결론 |
|---|---|---|---|
| 가능 | 가능 | 허용 | **C 모델 확정** — 테넌트별 `senderkey` + 내부 Ledger. 목표 구조 그대로 |
| 가능 | 가능 | **불가/별도 계약** | C 구조 + **재청구 대신 사장님 직접 결제**(우리는 발송만 대행). 또는 계약 체결 후 C |
| 가능 | **불가** | 허용 | **A로 베타 시작** — 우리 채널 1개. 템플릿을 최소로 유지해 C 전환 비용을 낮춘다 |
| **불가** | — | — | **Provider 재선정 검토**(다른 대행사에 동일 5개 질문) |

**코드 영향은 어느 쪽이든 작다** — `senderkey`를 환경변수에서 읽느냐(A) 테넌트 설정에서 읽느냐(C)의 차이뿐이고, `MessageProvider` 인터페이스 뒤라 dispatch·이벤트·로그는 그대로다.

## 2. 메시지 지갑(Ledger) 설계 — **아직 만들지 않는다**

### 2-1. 원칙: 돈은 `app_settings`에 넣지 않는다

현재 테넌트 설정은 `app_settings(key, value JSONB)`를 쓴다. 이건 **덮어쓰기 저장소**라
"지금 잔액이 얼마인지"만 남고 **왜 그렇게 됐는지가 남지 않는다.** 잔액은 분쟁이 생기는
값이므로 반드시 **변경 이력이 append-only로 쌓이는 별도 테이블**이어야 한다.

> **잔액은 저장하는 값이 아니라 거래의 합계로 도출되는 값이다.**
> (성능을 위해 캐시 컬럼을 둘 수는 있지만, 진실은 항상 거래 내역 쪽이다.)

### 2-2. 필요한 거래 종류

| 종류 | 언제 | 부호 | 비고 |
|---|---|---|---|
| `charge` | 사장님이 충전 | + | 결제 수단 연동 전까지는 관리자 수동 |
| `reserve` | 발송 직전 예약 차감 | −(보류) | 동시 발송으로 잔액이 마이너스가 되는 것을 막는다 |
| `capture` | 발송 성공 확정 | 예약을 확정 | `message_log.status = sent`와 1:1 |
| `release` | 발송 실패·skip | 예약 취소(환불) | 안 보낸 건 청구하지 않는다 |
| `adjust` | 관리자 조정 | ± | **사유 필수**. 누가 언제 왜 조정했는지 남긴다 |

`reserve → capture/release` 2단계를 두는 이유는 하나다 — **보내지도 않은 메시지 요금을
청구하지 않기 위해서**다. 단순 차감 방식이면 Provider 실패 때 환불 로직을 따로 만들어야 한다.

### 2-3. 개념 스키마 (migration 아님, 승인 후 작성)

```
tenant_message_ledger            -- append-only, UPDATE/DELETE 금지
  id, tenant_id, owner_username
  entry_type       charge | reserve | capture | release | adjust
  amount           numeric   (부호 포함)
  balance_after    numeric   (기록 시점 잔액 — 감사용 스냅샷)
  message_log_id   uuid null (reserve/capture/release는 발송 1건과 연결)
  reason           text null (adjust 필수)
  performed_by     text      (사장님 / admin / system)
  created_at
```

- `message_log`에 이미 있는 `provider_cost` / `platform_fee` / `tenant_charge` /
  `balance_before` / `balance_after`와 **역할이 겹치지 않는다** — 로그는 "이 메시지가 어떻게
  됐나", Ledger는 "돈이 어떻게 움직였나".
- 잔액 조회는 `sum(amount)`. 발송량이 커지면 테넌트별 캐시 컬럼 + 주기적 정합성 검사를 붙인다.
- **정합성 검사 항목**(정합성 감사에 추가할 후보): `sum(ledger) == 캐시 잔액`,
  `capture 건수 == sent 로그 수`, `reserve 중 미확정이 24h 이상 남아 있는 건`.

### 2-4. 가격 — 코드에 넣지 않는다

CPO가 예로 든 정액 차감(알림톡 15원 등)은 **운영이 쉬운 방식이지만 아직 확정 아님**이다.
설계상 지켜야 할 것은 하나다.

```
provider_cost   공급사가 알려준 실제 원가   ← Provider 응답에서만 채운다
platform_fee    우리 수수료                ← 정책 값
tenant_charge   사장님에게 실제 차감한 금액  ← Ledger의 capture 금액과 일치
```

단가는 **코드 상수가 아니라 설정값**으로 둔다. 원가가 바뀌거나 플랜별 무료 건수가 생겨도
배포 없이 바꿀 수 있어야 한다. 지금은 어떤 숫자도 넣지 않는다.

## 3. 메시지 관리 IA (Admin 전용, `[SOON]` 유지)

```
메시지 관리
├─ 발송 설정      이벤트별 ON/OFF (주문 접수 / 기사 배정 / 배송 완료)
│                  + 자동 발송 시 잔액 차감 동의(최초 1회)
├─ 메시지 템플릿   이벤트별 텍스트 템플릿 · 사용 변수 · 승인 상태
├─ 발송 내역      message_log 조회 (상태·사유·마스킹된 수신처)
├─ 잔액 / 충전    현재 잔액 · 거래 내역(Ledger) · 충전
└─ (향후) 공지 / 마케팅   ← 자동 발송 경로에 연결하지 않는다
```

**단계별 개방 순서**(CPO 확정): ① 운영 알림(자동) → ② 운영 공지(수동) → ③ 마케팅(수신동의 필요).
현재 화면은 ①의 ON/OFF 목록만 `준비 중`으로 노출하고 있고, 나머지는 **정보 구조만 잡아둔 상태**다.

### 지금 만들지 않는 이유
- 템플릿 편집 UI: 이미지·버튼·링크 규격이 모델(A/C)과 승인 절차에 종속된다. 알림톡은 **템플릿
  사전 승인이 필수**라 자유 입력 UI를 먼저 만들면 버려진다.
- 충전 UI: 결제 수단·정산 주체가 Q3 회신에 종속된다.
- 발송 내역 UI: 로그는 이미 쌓을 수 있으므로 **가장 먼저 열 수 있는 화면**이지만, 지금은 실제
  발송이 0건이라 화면을 만들 실익이 없다.
