## 0. 이번 조사에서 새로 확인한 사실 (기존 문서에 없던 것)

| 확인 | 결과 |
|---|---|
| `message_log.provider_cost / platform_fee / tenant_charge` 타입 | **`numeric(10,2)`** |
| `message_wallet` / `payments` 금액 타입 | **`bigint` (1/100원 정수)** |
| `platform_fee`를 쓰는 코드 | **없음** (컬럼만 존재, 항상 null) |
| 원장 transaction type | `charge / reserve / capture / release / adjust` 5종 |
| 잔액 부족 시 | reserve 실패 → 로그 `failed(insufficient_balance)`, **발송 없음·차감 없음** |

### ⚠ GAP — 금액 단위가 두 갈래다
```
wallet · payments · charge_intent   →  bigint,  1/100원 정수
message_log 의 돈 3개 컬럼          →  numeric(10,2)
```
지금 dispatch는 `tenant_charge`에 **1/100원 정수 값을 그대로** 넣는다(F3D-2 QA에서 `111`을
넣고 `111`로 읽었다). 값은 정확하지만, 컬럼 타입만 보면 **"111원"인지 "1.11원"인지 구분할 수
없다.** 지금은 사고가 나지 않았고, 나중에 이 컬럼으로 정산·세금계산서를 뽑을 때가 위험하다.

> **이번 단계에서 고치지 않는다**(설계 단계·DB 변경 금지). F3D-4 결정 항목으로 올린다.
> 선택지는 ① `numeric` 유지 + 단위를 "원"으로 명시 ② `bigint` 1/100원으로 통일(지갑과 일치).
> **②를 권고**한다 — 원장과 로그의 단위가 다르면 대조할 때마다 환산이 끼어든다.

## 1. 충전 모델 A / B / C 비교

| | **A 자유 충전** | **B 정액 상품** | **C 혼합(추천 금액 + 직접 입력)** |
|---|---|---|---|
| 사장님 행동 | 금액을 직접 입력 | 상품 선택 | 버튼 선택 또는 직접 입력 |
| 상품 테이블 | 불필요 | 필요 | **불필요**(추천 금액은 화면 상수) |
| PG 최소/최대 결제액 | 앱에서 검증 필요 | 상품이 곧 검증 | 앱에서 검증 필요 |
| 비정상 금액(0원·소수·과대) | 방어 필요 | 구조적으로 없음 | 방어 필요 |
| 보너스 도입 시 | 금액대별 규칙이 필요해짐 | 상품에 붙이면 끝 | 상품 도입으로 전환 필요 |
| 결제 실패 후 재시도 | 금액 재입력 | 같은 상품 재선택 | 쉬움 |
| **과거 데이터 오염 위험** | 없음 | **상품 단종 시 과거 결제의 근거 소실** → 정책 버전 관리 필요 | 없음 |

**권고: C(혼합), 단 "상품 테이블 없이" 시작.**
이유는 세 가지다.
1. 베타에서 정해야 할 것은 "얼마짜리 상품이 잘 팔리나"가 아니라 **"사장님이 메시지에 돈을 쓰는가"**다. 상품 구조는 그 답을 얻은 뒤에 만들어도 늦지 않다.
2. 상품을 지금 만들면 **상품에도 버전 관리가 필요**해진다(F3D-2에서 단가에 했던 것과 같은 이유). 지금 그 복잡도를 살 이유가 없다.
3. 추천 금액은 **화면의 버튼**일 뿐이므로, 나중에 B로 가더라도 버릴 코드가 거의 없다.

**대신 반드시 정해야 하는 것**(A/C의 유일한 약점): 금액 검증 규칙 — 최소·최대·단위(예: 원 단위 절삭 여부). 이건 세무·PG 답변과 무관하게 **CPO가 지금 정할 수 있는 사업 결정**이다.

## 2. 가격 구조 — 다섯 가지를 하나로 뭉개지 않는다

```
① Provider 원가        알리고에 우리가 내는 돈        (미확정 — TRACK A)
② 고객 차감액          사장님 지갑에서 빠지는 돈       tenant_charge   ← 유일하게 지금 구조가 있는 값
③ 플랫폼 수수료/마진    ② − ①                        platform_fee    ← 컬럼만 있고 아무도 안 씀
④ VAT                  과세 방식 미확정               (미확정 — 세무)
⑤ 최종 표시 금액        사장님 화면에 보이는 금액       (③④ 확정 후)
```

**핵심 구분**: ①은 *우리의 비용*이고 ②는 *사장님의 비용*이다. 둘이 같아지는 순간 우리는
메시지를 팔아 손익 0인 통신 대행업이 된다. 반대로 ②만 관리하고 ①을 기록하지 않으면
**마진이 얼마인지 사후에 계산할 수 없다.**

**권고**: `platform_fee`를 "계산해서 저장하는 값"으로 쓰지 말고 **`② − ①`의 파생값**으로 본다.
저장하려면 세 값이 항상 맞물려야 하는데(`②=①+③`), 원가가 나중에 정정되면 과거 행이 어긋난다.
→ **`provider_cost`(공급사가 알려준 값만)와 `tenant_charge`(실제 차감액)만 박제하고,
마진은 그 둘의 차이로 조회한다.** 이건 이미 F3D-2에서 "가짜 단가를 만들어 채우지 않는다"로
정한 원칙과 같은 방향이다.

> 지금 `platform_fee`가 항상 null인 것은 **버그가 아니라 정상**이다. 값을 만들 근거(원가)가 없다.

## 3. VAT — 외부 확인 질문 (지시하신 8개 + 실무 2개)

세무 전문가에게 그대로 물어볼 수 있는 형태로 정리했다.

| # | 질문 | 왜 필요한가 |
|---|---|---|
| 1 | 선불 충전 시점과 사용 시점 중 **언제 매출로 인식**하는가 | 충전형 SaaS의 근본 문제 |
| 2 | 충전액은 VAT **포함**인가 별도인가 | 화면 표시 문구가 갈린다 |
| 3 | 메시지 사용(차감) 시점에 별도 과세가 있는가 | 이중과세 여부 |
| 4 | 보너스(무상) 지급은 과세 대상인가 | 보너스 도입 가능 여부를 좌우 |
| 5 | 미사용 잔액 환불 시 VAT 처리 | 환불 정책의 전제 |
| 6 | 플랫폼 수수료의 과세 방식(중개 vs 재판매) | **TRACK A 알리고 답변과 직결** |
| 7 | 세금계산서 발행 주체는 우리인가 알리고인가 | 재판매 여부에 따라 달라짐 |
| 8 | PG 결제금액과 매출 인식 금액의 차이(PG 수수료) | 매출/비용 분리 |
| 9 | 사업자가 아닌 개인 사장님 결제 시 현금영수증 의무 | 베타 고객 구성상 실제로 발생 |
| 10 | 충전액에 유효기간이 없을 때 **장기 미사용 잔액의 회계 처리** | 부채로 남는 기간 |

**변경하지 않는 것**: `payments.amount = 고객이 실제 결제한 총액(VAT 포함)`.
답변이 오면 `supply_amount / vat_amount / payment_fee`를 **nullable로 추가**한다(과거 행은 null).
**⑥⑦은 알리고 답변 없이는 세무사도 답할 수 없다** — 두 트랙이 여기서 만난다.

## 4. 환불 — 시나리오별 원장 표현

원장은 append-only이고, **transaction type을 늘리지 않는다**(F3D-1 결정 유지).
```
adjust  +  reference_type='refund'  +  reference_id(원 payment/intent)  +  reason
```

| 시나리오 | 지갑 처리 | 결정 필요 |
|---|---|---|
| 충전 직후 전액 환불 | 충전액 전액 회수 | PG 수수료를 누가 부담하는가 |
| 일부 사용 후 환불 | **잔액 범위 내에서만** 회수 | 사용분은 환불 불가로 볼 것인가 |
| 전액 사용 후 환불 | 회수할 잔액 없음 | **환불 불가**가 기본 |
| 부분 환불 | 요청액 ≤ 잔액일 때만 | 부분 환불을 허용할 것인가 |
| 보너스 포함 | 현재 보너스 0이라 미발생 | 도입 시 "보너스 우선 소멸" |

**구조적 안전장치(이미 있음)**: 지갑 RPC가 **음수 잔액을 거부**한다. 따라서 "이미 쓴 돈을
환불해서 잔액이 마이너스가 되는" 사고는 정책 실수가 있어도 DB가 막는다.

**권고**: 베타에서는 **환불 UI를 만들지 않는다.** 발생 빈도가 낮고, 잘못 만들면 돈이 움직인다.
운영자가 `adjust + refund` 원장으로 처리하고 **PG 환불은 PG 콘솔에서** 수행한다.
자동화는 실제 요청이 반복해서 생긴 뒤에 만든다(STEP14 원칙: 관측된 것만 만든다).

## 5. 잔액 부족 — fail-safe는 **이미 구조로 보장되고 있다**

```
reserve 실패(insufficient_balance)
   → message_log: failed
   → provider 호출 없음 · 지갑 변동 없음
   → dispatchMessageEvent는 어떤 경우에도 throw하지 않는다
```
주문 생성 / 배송 상태 변경 / 기사 배정 / 배송 완료는 **메시지보다 먼저 DB에 저장된 뒤**
호출되므로, 잔액이 0이어도 업무는 그대로 끝난다. F3D-2 QA에서 "정책 없음 → 돈 이동 0"으로
같은 경로를 실측했다.

**결정 필요**: 잔액 부족을 사장님에게 **언제 알릴 것인가.**
- 발송 실패 후 사후 통지만 → 이미 놓친 뒤라 늦다
- 잔액이 임계 이하일 때 미리 배너 → **권고**. 임계값(며칠분/몇 건분)은 단가 확정 후 정한다.

문구는 F3D-1에서 고정한 문장을 유지한다.
> **"메시지가 발송되지 않아도 주문과 배송은 정상 처리되었습니다."**

## 6. 보너스 — 0 유지, 미래 구조만 기록

도입하면 **동시에** 필요해지는 것:
```
잔액을 두 갈래로 분리(충전금/보너스) → 차감 순서 → 환불 시 제외 → 소멸(유효기간) → 표시 UI
```
현재 지갑은 **단일 잔액 풀**이라 위 다섯이 전부 새 구조다.
장기 도입 시 권고 형태만 남긴다 — `lot`(충전 단위 묶음) 테이블 + FIFO 소진 + `expires_at`.
**지금 만들지 않는다.** 보너스보다 먼저 검증할 것은 *사장님이 메시지에 돈을 쓰는가*다.

## 7. 충전 상품 ≠ 가격 정책 (분리 유지)

```
Charging      "지갑에 얼마를 넣는가"     → Payment → Charge Intent → Wallet charge
Pricing       "1건에 얼마를 빼는가"      → Pricing Policy → reserve/capture → message_log
```
두 축이 독립이라 **단가를 v2로 바꿔도 이미 충전된 잔액은 영향받지 않고**, 충전 방식을 바꿔도
과거 발송의 가격 근거는 그대로다. F3D-2에서 이미 구조로 확인했다(과거 로그 불변 실측).

C안(상품 테이블 없음)을 택하면 이 분리는 **더 단순해진다** — 연결할 상품 id 자체가 없다.

## 8. 전체 돈 흐름과 각 금액의 의미

```
사장님
  │  충전 금액 선택 (추천 버튼 또는 직접 입력)      ← 검증: 최소/최대/단위 [결정 필요]
  ▼
Payment            amount = 고객이 실제 결제한 총액(VAT 포함)   ★ 재해석 금지
  │
  ▼ confirmed      confirmed_amount = PG가 실제 승인한 금액
  │
  ▼
Charge Intent      total_amount = 지급할 크레딧 (= wallet_amount + bonus_amount, 현재 bonus=0)
  │                ※ 결제 확인과 크레딧 지급은 다른 사건이다(F3C)
  ▼
Wallet charge      잔액 증가 — 원장에 append
  │
  ▼
메시지 발송
  │
  ▼
Pricing Policy     unit_price = 고객 차감 단가 (정책 id로 근거 박제)
  │
  ▼
reserve            잔액 부족이면 여기서 멈춤 → 발송·차감 없음, 업무는 정상
  │
  ▼
Provider           provider_cost = 공급사가 알려준 원가 (미연동이라 현재 null)
  │
  ├─ 성공 → capture   tenant_charge = 실제 차감액  +  price_policy_id = 근거
  └─ 실패 → release   차감 없음(예약 반환)
```

**같은 "금액"이라도 의미가 다섯 개다.** 결제 총액 / 승인액 / 지급 크레딧 / 차감 단가 / 공급사 원가.
이 문서의 목적은 이걸 영원히 섞지 않게 못 박는 것이다.

## 9. 사장님 UX 흐름 (숫자 없음)

```
[메시지 화면]
 현재 잔액  ────────────────  "충전하기"
      │
      ├─ 잔액 충분        → 평소 화면
      ├─ 잔액 임계 이하   → 배너: "잔액이 곧 소진됩니다"   [임계 기준 결정 필요]
      └─ 잔액 부족        → 배너: "잔액이 부족해 메시지가 발송되지 않습니다.
                                   주문과 배송은 정상 처리됩니다."

[충전]  금액 선택/입력 → 결제 → 결제 완료 → 충전 완료 → 잔액 반영
                              └ 결제 실패/취소 → 잔액 변화 없음, 재시도 안내
                              └ 결제됐지만 지급 처리 중 → "처리 중"으로 표시(F3D-1 규칙 유지)
```
- **"이번 발송 예상 차감"**은 단가가 확정된 뒤에만 보여준다. 지금 보여주면 거짓말이 된다.
- 충전/사용 내역은 **원장 그대로**를 보여준다(별도 집계 테이블을 만들지 않는다).

## 10. 상태 목록 — F3D-1 사장님 상태와의 충돌 점검

| 상태 | 근거 | F3D-1과 충돌 |
|---|---|---|
| 충전 시작 / 결제 대기 | `payments.created / pending` | 없음 |
| 결제 완료 | `payments.confirmed` | 없음 |
| 결제 실패 / 취소 | `payments.failed / cancelled` | 없음 |
| 충전 처리 중 | payment confirmed + intent pending | **F3D-1의 "처리 중"과 동일** — 유지 |
| 충전 완료 | `intent granted` + 원장 charge | 없음 |
| 충전 실패 | intent failed | Admin 목록 노출 필요(F3D-1 규칙) |
| 잔액 부족 | reserve 실패 | 없음 |
| 메시지 발송 실패 | log failed | 없음 |

**충돌 0.** 새 상태를 만들 필요가 없다 — 전부 기존 테이블의 상태 조합으로 표현된다.

## 11. Admin vs 사장님

| 사장님 | Admin |
|---|---|
| 잔액 · 충전 · 충전 내역 · 사용 내역 | 정책 관리 · 지갑 확인 · 운영 보정 · 환불(원장) |

**자동화 원칙 확인**: `Payment confirmed → Charge Intent grant`는 **F4에서 자동 연결**한다.
