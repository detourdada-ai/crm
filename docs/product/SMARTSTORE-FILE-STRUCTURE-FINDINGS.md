# 스마트스토어 실파일 구조 분석 — 등록 방식 정책 결정용 근거

- 일자: 2026-09-08 · 요청: CPO(등록 방식 정책 확정 전 파일 구조 확인)
- 분석 대상: user2 실제 업로드 파일 3개 (2026-09-04 / 09-07 / 09-08 내려받기)
- **구현 0건. 읽기 전용 분석.** 개인정보는 이 문서에 포함하지 않는다(식별자·상태값 통계만).

---

## 결론 3줄

1. **"파일에서 사라진 주문 = 취소"로 판단하면 안 된다.** 사라진 행 207건이 **전부 발송처리 완료건**이다.
2. **이 파일은 "전체 주문"이 아니다.** `발주발송관리` = **발송대기 스냅샷**이며, 취소 정보가 애초에 없다.
3. **중복 판정은 이미 정상 동작한다.** 3개 파일 모두 재업로드 시 100% "이미 등록됨"으로 걸러진다.

## 1. 파일 개요

| 내려받은 날 | 행 | 주문일 범위 | 일수 | 주문번호 | 상품주문번호 |
|---|---:|---|---:|---:|---:|
| 09-04 | 330 | 2026-08-23 ~ 09-04 | 13일 | 206 | 330 |
| 09-07 | 449 | 2026-08-30 ~ 09-07 | 9일 | 212 | 449 |
| 09-08 | 467 | 2026-08-30 ~ 09-08 | 10일 | 215 | 467 |

- 컬럼 **72개**, 3개 파일 헤더 **완전 동일**.
- **"전체 주문"이라는 이름과 달리 매번 기간이 다르다.** 09-04 파일은 8/23부터, 나머지는 8/30부터다.
  사장님이 내려받을 때 조회기간을 그때그때 다르게 잡은 것으로 보인다.
  **→ 파일명만으로 "전체"인지 판단할 수 없다.**

### 상태 컬럼 값 (3개 파일 전부 동일)
```
주문상태        : 발송대기  (1종, 전 행)
주문세부상태    : 발주확인  (1종, 전 행)
수량클레임 여부 : N        (1종, 전 행)
```

> 이 export는 **"발주/발송관리" 화면** 산출물이다. 즉 **아직 발송하지 않은 건만** 담긴다.
> **취소 주문은 이 파일에 애초에 실리지 않는다.**

## 2. ★ 행이 사라지는 진짜 이유 — 취소가 아니라 "발송처리 완료"

| 구간 | 사라짐 | 조회기간 밖으로 밀려난 것 | **조회기간 안인데 사라진 것** |
|---|---:|---:|---:|
| 09-04 → 09-07 | 156 | 61 | **95** |
| 09-07 → 09-08 | 112 | 0 | **112** |

**조회기간 안인데 사라진 207건(95+112)의 `발송일` 컬럼을 확인한 결과:**

```
발송일 있음 : 207건  (100%)
발송일 없음 : 0건
```

**전부 발송처리가 끝나서 "발송대기" 목록에서 빠진 것이다. 취소가 아니다.**

> 만약 "전체등록 시 파일에 없는 주문은 취소 처리"를 구현했다면,
> **9/7→9/8 한 번의 업로드만으로 정상 발송 주문 112건이 취소 처리**된다.
> 3일치 파일만으로 207건이다. 실제 운영에서는 매일 수십~수백 건이 잘못 취소된다.

## 3. 식별자 안정성 — 상품주문번호가 정답

전체 고유 상품주문번호 735개 중:

| 몇 개 파일에 등장 | 개수 |
|---|---:|
| 1개 | 355 |
| 2개 | 249 |
| 3개 | 131 |

**380개가 여러 파일에 걸쳐 같은 ID로 재등장한다** — 안정적인 행 단위 식별자로 확인됐다.
`주문번호`는 묶음 단위다(215종 vs 467행).

우리 시스템은 이미 이 구조를 쓰고 있다:
- 중복 판정 키 = `order_items.product_order_number` (STEP2에서 재설계 완료)
- `orders.internal_order_number`는 **스마트스토어 주문번호가 아니라 시스템 자체 생성 번호**(`202609080038` 형식)다. 대조할 때 이 컬럼을 쓰면 안 된다.

## 4. 중복 처리 검증 — 정상 동작

각 파일의 상품주문번호를 user2 테넌트 DB와 대조한 결과:

| 파일 | 상품주문번호 | DB에 이미 있음 | 신규 |
|---|---:|---:|---:|
| 09-04 | 330 | **330** | 0 |
| 09-07 | 449 | **449** | 0 |
| 09-08 | 467 | **467** | 0 |

**3개 파일 모두 지금 다시 업로드해도 중복 생성 0건이다.** 누적 파일을 매일 올리는
운영 방식이 이미 안전하게 지원되고 있다.

## 5. '전체 → 오늘' 전환 시 삭제 범위 시뮬레이션 (실제 삭제 안 함)

기준: 오늘 = 2026-09-08, 대상 = `import_id IS NOT NULL` 이면서 배송일이 오늘이 아닌 주문

```
user2 전체 주문 555건
 · 엑셀 유래(import_id 있음) : 553건   ← 삭제 후보
 · 수기 입력(import_id null) :   2건   ← 보호 대상
 · 배송일이 오늘이 아닌 것    : 513건   ← 실제 제거 대상
   제거 대상 배송상태: 배송대기 452 / 배송중 60 / 완료 1

[연쇄] 함께 지워질 배송건(order_shipments) : 996건
[연쇄] 그중 기사 배정된 건                 :  64건
[연쇄] 영향받는 배송그룹                   : 225개
        └ 통째로 비게 되는 그룹 188개 / 일부만 빠지는 그룹 37개
```

**주문 1건 삭제가 배송건·기사배정·배송그룹 3계층으로 번진다.** 배송그룹 225개 중 188개가
통째로 사라진다.

## 6. 정책 재검토가 필요한 지점

| CPO 정책 초안 | 이번 분석 결과 |
|---|---|
| 전체등록 = "파일이 현재 주문의 기준" | **성립하지 않음.** 발송대기 스냅샷일 뿐이고 기간도 매번 다르다 |
| 파일에 없는 주문 → 취소 판단 | **위험. 발송완료건을 취소 처리한다**(3일치에서 207건) |
| 취소 주문 반영 | 이 파일에 취소 정보가 **없다.** 다른 export(예: 취소/반품 관리)가 필요할 수 있다 |
| 전체 → 오늘 전환 시 기존 데이터 제거 | 기술적으로 가능하나 배송그룹 188개가 통째로 사라진다 |
| 중복 처리 | **이미 정상 동작**(100% 차단). 추가 작업 불필요 |

### CTO 의견 (결정은 CPO/CEO)

- **취소 반영은 이 파일로 불가능하다.** 스마트스토어에서 **취소/반품 내역이 나오는 다른
  export**를 받아 확인하는 것이 먼저다. 그 전에 취소 자동 반영을 만들면 오탐만 남는다.
- **중복 처리가 이미 완벽하므로, "매일 누적 파일을 그냥 올리는" 운영은 지금도 안전하다.**
  즉 등록 방식 전환/삭제 없이도 현재 방식이 성립한다 — 삭제 정책의 필요성 자체를
  다시 볼 여지가 있다.
- 삭제를 도입한다면 배송그룹 재생성까지 한 트랜잭션으로 묶어야 하며, 이는 별도 설계가 필요하다.

## 참고 — 분석 방법

파일 파싱·DB 대조 모두 읽기 전용이며, 개인정보는 통계로만 집계했다. `order_items.extra`에
업로드 원본 72개 컬럼이 그대로 보존되어 있어 과거 업로드분도 같은 방식으로 재분석할 수 있다.
