## 결론 먼저 — 승인 전에 알아야 할 3가지

1. **🔴 기존 취소 기능에 결함이 있다.** 주문을 취소해도 **배송건(`order_shipments`)이 취소되지
   않아 배송관리 보드·배송그룹·기사앱에 그대로 남는다.** 실측으로 확인했다.
   이걸 먼저 고치지 않으면 import 취소 반영을 붙여도 "취소했는데 기사한테 계속 뜬다"가 된다.
2. **🔴 파일 간 비교에 쓸 데이터가 현재 DB에 없다.** 이미 등록된 상품주문번호는 재업로드 시
   **아무것도 건드리지 않고 건너뛰므로**, "이 주문이 오늘 파일에 있었다"는 기록이 남지 않는다.
   비교 기준을 새로 만들어야 한다(추가 컬럼 1개 또는 원본 파일 재파싱).
3. **🟡 파일마다 조회 기간이 다르다.** 실측: 13일치 / 9일치 / 10일치. 기간이 겹치지 않는
   구간까지 "사라졌다"로 판정하면 **정상 주문 61건이 오탐 취소**된다(9/4→9/7 실측).

## A. 현재 import 구조

### 저장되는 것
| 대상 | 컬럼 | 비고 |
|---|---|---|
| `orders` | `import_id`, `delivery_status`, `cancelled_at`, `delivery_date`, `order_date` | 어느 import가 만든 주문인지 알 수 있음 |
| `order_items` | `product_order_number`, `extra`(원본 행 72컬럼), `created_at` | **`import_id` 없음** |
| `imports` | `created_at`, `file_path`(STEP19 원본) | |

### 동일 상품주문번호 재업로드 시 현재 동작
`import.service.ts`의 중복 분기는 이렇게 되어 있다.

```
Case C: 이 부모 주문의 상품주문이 전부 이미 등록됨 — 그룹 전체를 건너뛴다.
        기존 주문/배송/기사배정 등은 아무 것도 건드리지 않는다.
```

**→ 재업로드는 완전한 no-op이다.** 그래서 "이 상품주문번호가 오늘 파일에도 있었다"는 사실이
**어디에도 기록되지 않는다.** 이것이 이번 기능의 핵심 제약이다.

## B. 파일 간 비교 기준 — 3가지 방안

| 방안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **B-1** `order_items`에 마킹 | `last_seen_import_id`(또는 `last_seen_at`) 컬럼 추가. 파일에 등장한 행은 신규/기존 관계없이 **UPDATE**로 도장을 찍는다 | 비교가 단순한 쿼리 1개. **DELETE 없음**(CPO 금지사항 준수). 과거 데이터도 null로 안전 | nullable 컬럼 1개 추가(마이그레이션) |
| **B-2** 원본 파일 재파싱 | STEP19로 보관 중인 직전 파일을 다시 파싱해 비교 | 스키마 변경 0 | 원본은 2026-09-08부터만 있고 **30일 후 파기**된다. 파기 후 비교 불가. 업로드마다 xlsx 파싱 1회 추가 |
| **B-3** 스냅샷 테이블 | `import_product_order_numbers(import_id, pon)` | 이력이 완전히 남음 | 신규 테이블 + 파일당 수백 행 누적 |

**CTO 추천: B-1.** 이유는 (a) DELETE 없이 UPDATE만으로 끝나고, (b) 30일 파기 정책과 무관하게
동작하며, (c) 신규 테이블 없이 nullable 컬럼 1개면 된다. B-2는 보관정책과 결합되어
"원본이 파기되면 취소 판정이 멈추는" 숨은 의존이 생겨 권하지 않는다.

### ⚠ 비교 범위는 반드시 "겹치는 기간"으로 한정해야 한다
실측한 파일 3개의 주문일 범위:

```
09-04 파일: 2026-08-23 ~ 09-04 (13일)
09-07 파일: 2026-08-30 ~ 09-07 (9일)   ← 8/23~8/29가 통째로 빠짐
09-08 파일: 2026-08-30 ~ 09-08 (10일)
```

09-04 → 09-07에서 사라진 156건 중 **61건은 취소가 아니라 새 파일의 조회기간 밖**이다.
비교를 기간 한정 없이 하면 이 61건이 전부 오탐 취소된다.

**제안: 이번 파일의 주문일 최소값 이상인 기존 주문만 비교 대상으로 삼는다.**
(= 이번 파일이 커버하는 구간에 대해서만 "있었는데 없어졌다"를 판정)

### 케이스별 예상 동작 (B-1 기준)

| # | 케이스 | 동작 |
|---|---|---|
| 1 | 신규 주문 | 기존과 동일하게 INSERT + 도장 |
| 2 | 기존 주문(파일에 계속 있음) | INSERT 없이 **도장만 갱신** (현재는 완전 no-op) |
| 3 | 기존 주문이 오늘 파일에서 사라짐 | 파일 커버 구간 안 + 도장이 이번 import가 아님 → **취소 전환** |
| 4 | 동일 주문 여러 번 업로드 | 도장만 갱신, 중복 생성 0 (기존 정책 유지) |
| 5 | 날짜 건너뛰고 업로드 | **아래 Case 7 참조 — 정책 결정 필요** |
| 6 | 동일 파일 재업로드 | 전 행에 도장 갱신 → 사라진 것 0건 → **취소 전환 0건**. 이미 취소된 건은 파일에 없으므로 그대로 유지(잘못된 복구 없음) |

### Case 7(며칠 건너뛴 업로드) — 임의로 정하지 않고 보고합니다
9/7 업로드 후 9/10에 업로드하면, 9/8·9/9에 발송대기였다가 빠진 건이 한꺼번에 잡힌다.
**B-1 방식은 "직전 파일"이 아니라 "마지막으로 본 시점"과 비교하므로 건너뛰어도 논리적으로는
동일하게 동작한다**(도장이 오래된 건 = 그 사이 사라진 건). 다만 한 번에 대량 취소가 발생할 수
있으므로 **확인 절차를 둘지**가 정책 판단이다.

> **CTO 제안: 취소 대상이 N건 이상이면 즉시 반영하지 않고 "취소 예정 N건" 확인 단계를 둔다.**
> 업로드 결과 화면에 이미 신규/중복 건수를 보여주고 있으므로 같은 자리에 붙일 수 있다.

## C. 🔴 취소 상태 영향 — 기존 로직에 결함 발견

### 실측 결과 (`step22-cancel-propagation-probe.ts`, user3에서 생성→검증→삭제)

```
[취소 전] 배송보드 포함 / 배송그룹 대상 포함
orders.delivery_status          : 취소     (cancelled_at 설정됨)
order_shipments.delivery_status : 배송대기  (cancelled_at null)

배송관리 보드에 남아 있는가 : ★ 예 (남는다)
배송그룹 대상에 남아 있는가 : ★ 예 (남는다)
```

**원인**: 코드베이스 전체에서 `delivery_status: "취소"`로 UPDATE하는 곳은
`orders.repository.ts`의 `cancelOrder` **단 하나**이며, `order_shipments`를 취소로 바꾸는
코드는 **존재하지 않는다.**

그런데 배송 관련 화면은 전부 배송건 기준으로 조회한다:
- 배송보드 `findByDeliveryDate` → `.neq(shipments.delivery_status, "취소")`
- 배송그룹 `findEligibleForGrouping` → 같은 필터
- 기사앱 `findByDriverIdAndDeliveryDate` → 같은 필터
- 그리고 `toBoardRows`는 **부모 주문의 상태로 거르지 않는다**(주문이 존재하는지만 확인)

| 화면 | 기준 | 취소 반영 |
|---|---|---|
| 주문 목록 / 상세 | `orders.delivery_status` | ✅ 반영됨 |
| 배송관리 보드 | `order_shipments.delivery_status` | ❌ **안 됨** |
| 배송그룹 | 〃 | ❌ **안 됨** |
| 기사 배정 / 기사앱 | 〃 | ❌ **안 됨** |

> 운영에 취소 주문이 **0건**이라 지금까지 아무도 겪지 않았다. 하지만 이번 기능이 들어가면
> **매일 수십 건이 이 경로를 탄다.**

**따라서 import 취소 반영보다 이 결함 수정이 먼저다.** 그렇지 않으면 "취소했는데 기사앱에
계속 뜨는" 상태가 대량으로 발생한다.

## D. 배송 진행 중인 주문이 파일에서 사라지는 경우

현재 `cancelOrder`의 방어선:
- `.neq("delivery_status", "완료")` → **배송완료 주문은 취소되지 않는다**(이미 보호됨)
- `driver_id: null` → 단, 이건 `orders.driver_id`만이고 `order_shipments.driver_id`는 남는다
- **배송중(진행 중) 주문은 취소가 가능하다**

**DELETE·cascade는 발생하지 않는다.** `cancelOrder`는 UPDATE만 하고, 배송그룹은
`triggerDeliveryGroupRegeneration`으로 재계산될 뿐 그룹 행을 지우지 않는다.
→ **CPO의 "데이터 보존, 상태만 변경" 요건은 구조적으로 충족 가능하다.**

### 결정이 필요한 것
**이미 기사가 배송 중인 주문이 파일에서 사라지면 자동 취소해도 되는가?**
- 실측상 user2에 배송중 60건이 있다.
- CTO 의견: **배송중은 자동 취소에서 제외하고 "확인 필요"로 표시**하는 편이 안전하다.
  기사가 실제로 물건을 들고 있는데 시스템만 취소되면 현장과 어긋난다.
- 다만 이는 CPO 정책 판단이라 임의로 정하지 않았다.

## 오늘 주문 건수 계산 조건 (질문하신 부분)

현재 구조 그대로 쓰면 된다 — 새 조건이 필요 없다.

```
유효 주문  = orders 中 delivery_status != '취소'          (주문 목록/건수)
배송 대상  = order_shipments 中 delivery_status != '취소'  (배송보드/기사앱)
```
