## 1. 현재 `가져올 주문 범위` — **그대로 유지**

```
○ 오늘 주문 가져오기      ○ 특정 날짜 주문 가져오기      ○ 전체 주문 가져오기
```

의미도 그대로다: **"이 파일에서 어떤 행을 등록할지"** 정하는 **입력 필터**.
이 컨트롤에 최신화 의미를 얹지 않는다 — 기존 사용자의 동작이 조용히 바뀌면 안 되기 때문이다.

## 2. `접수 방식` 신설 (최소 UI)

`가져올 주문 범위` **위에** 라디오 2개를 둔다. 순서가 중요하다 — "이 파일로 무엇을 할지"를
먼저 정하고, 그 다음 "어떤 행을 가져올지"를 정하는 것이 사고 순서와 맞는다.

```
📥 접수 방식
   ● 누적 등록                                     ← 기본값
     이번 파일의 주문을 기존 주문에 추가·수정합니다.
     파일에 없는 기존 주문은 그대로 유지됩니다.

   ○ 당일 배송 최신화
     선택한 배송일의 배송 목록을 이번 파일로 교체합니다.
     그 배송일에서 이번 파일에 없는 배송건은 배송 대상에서 제외됩니다.
     └ 최신화할 배송일  [ 2026-09-08 ▾ ]        ← 최신화 선택 시에만 노출
```

- 라디오 2개 + 날짜 입력 1개. **새 화면·새 단계 없음.**
- "당일 배송 최신화"를 고르면 **경고 배너**를 띄운다(기존 `전체 주문 가져오기` 경고와 같은 형식):
  > ⚠️ 선택한 배송일(2026-09-08)의 배송건 중 이번 파일에 없는 건은 배송 대상에서 제외됩니다.
  > 다른 배송일과 직접 입력한 주문은 영향을 받지 않습니다.

### 왜 "선택한 배송일"을 사용자에게 받는가
파일에 등장한 배송일을 자동으로 전부 최신화 대상으로 삼으면, **실제 파일이 9/8~9/18
9개 날짜에 걸쳐 있으므로 미래 예약 배송분까지 한꺼번에 최신화 대상**이 된다. 너무 넓고
위험하다. 사장님이 "오늘 배송분을 맞춘다"는 의도를 정확히 표현하려면 **날짜 1개를
명시적으로 고르는 것**이 맞다.

기본 선택값은 **오늘(KST)** 로 채워두되 바꿀 수 있게 한다.

## 3. 선택별 정확한 처리 범위

### ① 누적 등록 (기본 — 현재 동작과 100% 동일)

| 대상 | 처리 |
|---|---|
| 파일의 신규 상품주문 | 등록 (현행 그대로) |
| 파일의 기존 상품주문 | 중복 판정으로 건너뜀 (현행 그대로) |
| **파일에 없는 기존 주문/배송건** | **아무것도 하지 않음** |
| 자동 취소 | **없음** |

→ **코드 동작 변화 0.** 기존 사장님은 아무것도 바꾸지 않아도 지금과 똑같이 동작한다.

### ② 당일 배송 최신화

**대상 집합**(전부 `order_shipments` 기준, tenant scope 필수):

```
최신화 대상 =
    order_shipments
    WHERE tenant_id  = 내 사업장
      AND delivery_date = 선택한 배송일 (KST 캘린더일)
      AND delivery_status NOT IN ('완료', '취소')      ← 완료/이미취소 제외
      AND 부모 orders.import_id IS NOT NULL             ← 수기 주문 제외
```

**판정**:

| 배송건 | 처리 |
|---|---|
| 이번 파일에 있음 | 유지(+ 기존 등록 로직대로 신규 상품주문 추가) |
| **이번 파일에 없음** | **`cancelMany`로 취소** — 배송보드·그룹·기사앱에서 제외 |
| 완료 | **건드리지 않음** |
| 이미 취소 | 건드리지 않음(재취소로 `cancelled_at`이 덮이지 않게) |
| 수기 주문(`import_id IS NULL`) | **건드리지 않음** |
| **다른 배송일** | **건드리지 않음** |

**"파일에 있음"의 판정 키**: `order_items.product_order_number` → `shipment_id`.
STEP22-1의 `last_seen_import_id`가 이번 import로 갱신된 품목이 속한 배송건이 곧 "파일에 있는 것"이다.
**여러 날짜/여러 import를 거슬러 비교하지 않는다** — 이번 파일 하나와 선택한 배송일 하나만 본다.

**물리 DELETE 없음.** 상태만 바꾸고 배정·그룹·이력은 보존한다(STEP22-0에서 검증된 경로 재사용).

## 4. 배송건 단위 최신화 설계 (핵심)

```
사장님: 접수 방식 = 당일 배송 최신화, 배송일 = 9/8
        ↓
[분석 단계]  파일 파싱 → 옵션의 "날짜 선택"으로 배송일 산출
        ↓
[미리보기]  9/8 기존 배송건 A개
            그중 이번 파일에 있는 것 B개
            → 제외 예정 (A − B)개   ← 확정 전에 반드시 보여준다
        ↓
[사장님 확인]
        ↓
[확정]  기존 등록 로직 그대로 실행
        + 제외 대상 배송건에 cancelMany
        + syncOrdersFromShipments로 orders 파생
        + 그 배송일만 배송그룹 재계산
```

### 안전장치 3가지 (설계에 반드시 포함)

1. **제외 예정 건수를 확정 전에 보여준다.** 확정 화면에 이미 신규/중복/이미등록 카운트를
   보여주고 있으므로 같은 자리에 한 줄 추가하면 된다. 숫자를 보지 않고 취소가 일어나면 안 된다.
2. **"파일에 그 배송일 배송건이 0건"이면 진행을 막는다.** 날짜를 잘못 고르면 그 날 전체가
   취소된다 — 가장 위험한 오조작이다. 0건이면 경고하고 확정 버튼을 비활성화한다.
3. **배송중은 정책 미확정이므로 이번 설계에서 제외 대상에 넣지 않는다.**
   후보로는 세되 "확인 필요 N건"으로 따로 보여주고 자동 취소하지 않는다. (CEO 판단 대기)

### 구현 시 걸림돌 하나 (미리 보고)
배송일은 **옵션 텍스트를 파싱해야** 나온다(`parseDeliveryDateFromOption`). 현재 이 파싱은
**확정 단계(`runImport`)에서만** 일어나고 분석 단계에는 없다. 위 미리보기를 만들려면
**분석 단계에서도 같은 파싱을 한 번 해야 한다**(같은 함수 재사용이라 로직 중복은 없다).
이건 기존 import 구조 변경이 아니라 분석 응답에 필드를 추가하는 수준이다.

대상에서 빠진다.** 한 번 켜두고 잊어버리는 것이 가장 위험한 시나리오다. 취소를 유발하는
선택은 매번 의식적으로 하게 하는 편이 안전하다.

> 기존 `import_order_scope` 설정(가져올 주문 범위 기억)은 **그대로 둔다.** 이번에 건드리지 않는다.

| # | 사안 | 제안 |
|---|---|---|
| ① | 최신화 대상 배송일을 **사용자가 고르게** 할지, 파일에 등장한 날짜를 자동으로 쓸지 | **사용자 선택**(기본값 오늘). 자동은 미래 예약분까지 휩쓴다 |
