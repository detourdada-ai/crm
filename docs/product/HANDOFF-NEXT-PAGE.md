## 4. 남은 실제 업무 3트랙

### A. hnd1 성능 검증 ⏳
CEO가 Vercel → Settings → Functions → Function Region → **Tokyo(hnd1)** 로 바꾸고 **재배포**해야 한다
(리전은 새 배포부터 적용). 2026-09-07 기준 `x-vercel-id`는 여전히 `icn1::iad1::`.

CTO는 그 뒤에 ① `icn1::hnd1::` 확인 → ② `scripts/qa/perf-core-flow-latency.ts` 동일 조건 5회 →
③ median 비교. **목표값을 임의로 만들지 않는다.**

| STEP17 기준값(iad1, 2026-09-07) | |
|---|---|
| PC → Supabase(도쿄) 직접 왕복 | **109ms** |
| 배송보드 GET warm TTFB | **1,174ms** |
| 변경사항 저장 | 서버 **1,684ms** / 총 **2,750ms** |
| 주문 상세 GET TTFB | **1,198ms** |
| 기사앱 배송완료 | 서버 **1,880ms** / 총 **2,049ms** |

> 결론(STEP17): 거의 아무 일도 안 하는 GET조차 TTFB 1.1~1.2초인데 DB 직접 왕복은 109ms다.
> **DB가 느린 게 아니라 함수가 멀다.** A(리전)를 걷어내기 전에 D(순차 처리)·C(다운로드)를
> 만지면 효과를 측정할 수 없다.

### B. STEP14 실사용 검증 ⏳

미확정: 알리고 다중 발신프로필 · 사업자별 발송 구조 · 위임/대행 가능 여부 · 원가/정산 ·
VAT · PG 선불충전 · 충전 최소금액 · 세금계산서/현금영수증.
**답변 전에는 실제 발송·결제·과금 기능을 열지 않는다.**
발송용 질문서(알리고 10문 / 세무 11문): `docs/product/STEP15-F3D-3-STEP2-EXTERNAL-INQUIRIES.md`.

> 공개 자료로 확인된 것: 알림톡 6.5원 / 대체문자 8.4원 표기(부가세 포함 여부 명시 없음).
> **카카오는 민원 누적 시 사업자등록번호 단위로 차단**할 수 있고 발송 책임은 발신 사업자에게 있다
> → 플랫폼이 자기 사업자로 여러 사장님 발송을 대신하면 **한 사장님의 민원이 전체를 멈출 수 있다.**
> 이건 가격이 아니라 아키텍처 문제이며 알리고 Q2·Q4 답에 달렸다.

## 5. 고정 IP 서버 — 지금 만들지 않는다

들어갈 자리는 **DB 경로가 아니라 외부 API 경로**다. `Vercel → 고정 IP 서버 → Supabase`로
일반 CRUD를 우회시키면 홉이 늘어 현재 병목(A)이 오히려 악화된다.

가치가 생기는 조건: **알리고/PG의 IP 화이트리스트 요구** 또는 **실제 background worker 필요**.
그때는 단순 서버가 아니라 **Tokyo Worker + Queue + 외부 API Gateway**로 묶어 아키텍처부터 논의한다.
후보 작업: 알리고 호출 대행 · PG 웹훅 · 대량 import · 지오코딩 · 그룹 재계산.

## 7. 참고 — 절대 규칙 (계속 유효)

- 돈: `PG 결제 ≠ Wallet 충전 ≠ 메시지 차감`. 금액은 **1/100원 정수**. 원장 append-only
  (**FK 정리·시스템 트랜잭션은 막지 않는다** — 0055/0058에서 두 번 사고 났다).
- **가격 정책이 없으면 reserve조차 하지 않는다** → 발송 0 · 지갑 이동 0. 지금 이게 정상 상태다.
- 과거 로그는 `tenant_charge`(얼마) + `price_policy_id`(왜)로 영구 증빙. 역채우기 금지.
- 랜딩: 이름은 예외 없이 `성○이름`, 전화번호·상세주소 생성 금지, **개인정보 포함 실화면 캡처 금지**,
  가짜 후기·만족도·절감률 금지. 후기 데이터가 비면 섹션이 스스로 사라진다
  (`src/lib/constants/testimonials.ts`에 실제 발언만 추가하면 코드 수정 없이 노출).
- Production DB 쓰기 스크립트는 `scripts/safe-scratch.ts`의 `withSnapshot()`을 통해서만.
