# STEP14 — 실사용 발견 기록 & 대응 (REAL USAGE DISCOVERY & RESPONSE)

> 개설 2026-09-04 / 운영 방식 확정 2026-09-05(CPO 작업지시).
> **새 기능을 만드는 스프린트가 아니다.** 실제 사용 중 발생한 문제를
> `발견 → 재현 → 분류 → 최소 수정 → 재검증`으로 처리한다.
>
> 지금 이 프로젝트의 가장 중요한 질문은 하나다.
> **사장님이 주문:한장을 쓰다가 어느 순간 다시 엑셀·카카오·전화로 돌아가는가?**
>
> **성공 기준(CPO, 2026-09-07):** "몇 개를 고쳤는가"가 아니라
> **"실제 사용에서 어디가 제품의 한계로 드러났는가"** 를 찾는 것이다.
> 수정 건수가 0이어도 한계를 정확히 찾아냈다면 이 단계는 성공이다.

## 1. 기록 방식 (CEO/CPO — 길게 쓸 필요 없음)

아래 블록을 복사해 §5에 붙인다. 해결책은 적지 않는다(해결책을 적기 시작하면 관찰이 아니라 설계가 된다).

**CEO는 앞의 네 줄만 채우면 된다.** 완벽하게 정리할 필요 없다 — 날것 그대로 던져도 된다.
이후 `관찰 → 재현 → 분류 → 제품 판단`은 CPO가 맡고, CTO가 실행한다.

```text
[STEP14-00N]

상황:
행동:
문제:
결과:
기존 방식:   ← 선택. 기억나면만
```

## 2. CTO 처리 절차 (기록이 들어오면 즉시)

순서를 반드시 지킨다 (CPO, 2026-09-07):
**관찰 → 재현 → 원인 확인 → A/B/C/D 분류 → 제품 판단 → (필요한 경우) 수정 → 회귀**

1. 실제 화면에서 재현
2. **원인 확인** — 버그인지 / UX인지 / 정책 문제인지. 원인을 모른 채 분류하지 않는다
3. 기존 정책 확인
4. **A/B/C/D 분류**
5. **제품 판단** — 고칠 문제인지, 고칠 만한 문제인지. **"고칠 수 있다"가 "고쳐야 한다"는 아니다**
6. 수정 (**필요한 경우에만**)
7. 회귀 게이트 실행([REGRESSION-GATE](../qa/STEP13-PHASE-B/REGRESSION-GATE.md) §1 해당 영역)
8. baseline cleanup 확인(diff = 0)

중간 Gate마다 보고하지 않는다. `발견 → 원인 → 수정 → 재검증 → 다음 발견`으로 이어가고 §6 형식으로만 최종 보고한다.

## 3. 분류 기준 (CPO 라벨, **2026-09-07 재정의**)

| 분류 | 뜻 | 예 | CTO 권한 |
|---|---|---|---|
| **A 실제 버그** | 현재 정의된 기능이 의도대로 동작하지 않음 | 저장 후 값이 사라짐, 필터 결과가 조건과 다름, 다른 테넌트 데이터 노출 | **재현되면 자율 수정** |
| **B UX / 사용성** | 기능은 정상인데 멈추거나, 못 믿거나, 용어를 모름. 현재 제품 범위 안에서 명확히 개선 가능 | 다음 단계가 안 보임, 저장됐는지 확신 없음, 용어 이해 못 함 | **제품 의도가 명확한 경우 수정** |
| **C 정책 / 운영 문제** | 기존 **정책의 해석이나 운영 방식** 확인이 필요함 | "이 건은 원래 여기서 처리하는 게 맞나", 기본값·보존·처리 대상 범위 해석 | **임의 변경 금지 — CPO 판단 요청** |
| **D 신규 기능 / 범위 / 정책** | 현재 제품이 제공하지 않는 기능 | 카카오 자동 연동, 재고, 경로 최적화, 권한 범위 확대 | **반드시 STOP.** CEO/CPO 판단 없이 구현하지 않는다 |

> **⚠ 2026-09-07 변경점 — 예전 기록과 라벨이 다르다.**
> 이전 표(2026-09-05)에서 **C는 "기존 도구 복귀"** 였으나, 오늘 CPO가 **C를 "정책/운영 문제"** 로
> 재정의했다. **기존 도구 복귀는 이제 분류가 아니라 관찰 트리거**(§4의 3·6번)이며,
> **§4-1의 다섯 갈래로 원인을 확정한 뒤 A·B·C·D 중 하나로 귀결시킨다.**
> §5에 남은 2026-09-05 이전 기록의 C 라벨을 오늘 기준으로 읽지 말 것.

> 기존 도구 복귀가 여전히 **가장 중요한 발견**이라는 점은 그대로다.
> "기능이 없어서 불편하다"보다 **"기능이 있는데도 결국 엑셀을 다시 열었다"** 가 훨씬 중요하다.

## 4. 기록해야 할 순간 (사소해 보여도 기록)

| | 순간 | 예 |
|---|---|---|
| **1** | **멈춤** | 어디를 눌러야 할지 모름 · 용어를 이해 못 함(동일인 후보·상품행·배송그룹·일괄 적용·변경사항) · 다음 행동을 고민함 · 제품 메뉴 순서와 실제 업무 순서가 다름 |
| **2** | **되돌아감** | 이전 화면으로 다시 감 · 같은 정보를 다시 확인 · 이미 입력한 내용을 다른 곳에서 다시 찾음 |
| **3** | **외부 도구 복귀** | 엑셀 열기 · 카카오 확인 · 전화 확인 · 기사에게 별도 전달 |
| **4** | **불안해서 확인** | 시스템 결과를 믿지 못하고 별도로 다시 확인 — "이거 저장된 거 맞나?" "전체 주문이 들어간 건 아닌가?" "취소 건도 같이 들어갔나?" "기사에게 제대로 전달됐나?" |
| **5** | **중복 입력·중복 확인** | 같은 정보를 여러 번 입력함 · 같은 것을 두 곳에서 확인함 |
| **6** | **작업 이탈** | 하던 작업을 중단하고 **다른 방법으로 처리해버림** (제품 밖에서 끝냄) |

> **4번은 기능 부족이 아니라 신뢰 UX 문제일 가능성이 크다.** 기능을 추가하기 전에
> "지금 무엇이 반영됐는지"를 보여주는 것으로 해결되는지 먼저 본다.
>
> 3번을 기록할 때는 **직전 행동까지** 함께 남긴다(예: "기사 배정까지 하고 나서 카카오를 열어 다시 전달") — 재현과 원인 분리가 정확해진다.
>
> **6번은 3번보다 심각하다.** 3번은 제품을 쓰다가 잠깐 나간 것이고, 6번은 **제품을 포기한 것**이다.

### 4-1. 외부 도구로 갔을 때 — 원인부터 확인한다 (CPO 원칙, 2026-09-07)

> **사용자가 외부 도구를 썼다는 사실만으로 "그 기능이 필요하다"고 결론 내리지 않는다.**
> 이것이 STEP14에서 가장 틀리기 쉬운 지점이다. 관찰을 곧바로 기능 요구로 번역하면
> 우리가 피하려던 "기능 많은 SaaS"로 그대로 돌아간다.

3·6번을 기록했으면 **아래 5개 중 어디인지 먼저 확정한 뒤에** 제품 판단을 한다.

| | 왜 외부 도구로 갔는가 | 귀결 | 대응 |
|---|---|---|---|
| ① | **기능이 없어서** | D | STOP → CEO/CPO 판단. 구현하지 않는다 |
| ② | **기능은 있는데 못 찾아서** | B | 발견 가능성 문제 — 배치·라벨·진입점 |
| ③ | **기능은 있는데 못 믿어서** | B (또는 A) | 신뢰 UX. **결과가 실제로 틀렸다면 A 버그다** |
| ④ | **그냥 기존 습관이라서** | — | **고치지 않는다.** 기록만 남기고 반복되는지 본다 |
| ⑤ | **현재 정책상 제품에서 처리할 대상이 아니라서** | C | 정책 확인 → CPO 판단. 임의 변경 금지 |

④와 ①은 겉으로 똑같아 보이지만 대응이 정반대다. **구분하지 못하면 분류하지 않고 CPO에게 올린다.**

## 7. 경계

**자율**: QA 노후화 · flaky·상태 오염 · 범위 내 제품 버그 · UX 명확화 · 용어 개선 · 안내 추가 · 기존 흐름 연결 개선 · cleanup · baseline 재측정 · 회귀 실행 · 정적/배포 검증.

**금지**: assertion 삭제 · 대상 축소 · sleep으로 억지 PASS · 무한 retry · **발견되지 않은 신규 기능 선제 구현** · **성능 최적화**.

> **성능은 이번 단계의 대상이 아니다(CPO, 2026-09-07).** hnd1 전환으로 저장이 1초 내외가 됐고
> (`docs/qa/STEP18-HND1-REGION/FINAL-REPORT.md`), CPO가 D 404ms·F1·DB 최적화를 **전부 ❌로 닫았다.**
> 지금 필요한 것은 404ms를 더 줄이는 게 아니라 **사장님이 이 속도를 어떻게 느끼는지**다.
> 실사용에서 "느리다"는 관찰이 나오면 그것도 발견으로 기록해 분류한다 — 관찰 없이 먼저 손대지 않는다.

**BLOCKER 4종**(①제품 정책 ②비가역 데이터 ③권한·보안 ④신규 기능/범위 확대)은 `현상 → 재현 → 근거 → 영향 범위 → 선택지`까지만 정리하고 멈춘다.

**수정 후 최소 QA**: 해당 기능 QA + 영역 필수 회귀 + (영향 시) user3/user6 격리 + cleanup baseline diff = 0 + tsc·ESLint·Build·Production·git clean. 제품 화면 구조가 바뀌면 [Landing Product Parity Gate](../qa/STEP13-PHASE-B/REGRESSION-GATE.md#1-1-landing-product-parity-gate-cpo-결정-2026-09-05)도 적용한다.
