# STEP14 — 실사용 발견 기록 & 대응 (REAL USAGE DISCOVERY & RESPONSE)

> 개설 2026-09-04 / 운영 방식 확정 2026-09-05(CPO 작업지시).
> **새 기능을 만드는 스프린트가 아니다.** 실제 사용 중 발생한 문제를
> `발견 → 재현 → 분류 → 최소 수정 → 재검증`으로 처리한다.
>
> 지금 이 프로젝트의 가장 중요한 질문은 하나다.
> **사장님이 주문:한장을 쓰다가 어느 순간 다시 엑셀·카카오·전화로 돌아가는가?**

## 2. CTO 처리 절차 (기록이 들어오면 즉시)

1. 실제 화면에서 재현
2. 기존 정책 확인
3. **A/B/C/D 분류**
4. 수정 가능 여부 판단
5. 수정
6. 회귀 게이트 실행([REGRESSION-GATE](../qa/STEP13-PHASE-B/REGRESSION-GATE.md) §1 해당 영역)
7. baseline cleanup 확인(diff = 0)

중간 Gate마다 보고하지 않는다. `발견 → 원인 → 수정 → 재검증 → 다음 발견`으로 이어가고 §6 형식으로만 최종 보고한다.

## 3. 분류 기준

| 분류 | 뜻 | 예 | CTO 권한 |
|---|---|---|---|
| **A 제품 버그** | 의도된 기능이 정상 동작하지 않음 | 저장 후 값이 사라짐, 필터 결과가 조건과 다름, 다른 테넌트 데이터 노출 | **자율 수정** |
| **B UX·흐름** | 기능은 정상인데 사용자가 멈추거나 못 믿음 | 다음 단계가 안 보임, 용어를 모름, 결과를 믿기 어려움, 같은 일을 엑셀에서 다시 함 | **정책 불변 범위에서 최소 수정** |
| **C 정책 판단** | 기존 동작·기본값·보존·권한이 바뀜 | 주문 범위 기본 정책 변경, 자동 처리 여부, 권한 범위 | **수정 금지** — 근거와 선택지만 보고 |
| **D 신규 기능** | 현재 구조로 해결 불가 | 카카오 자동 연동, 재고, CRM 확장, 경로 최적화, AI | **즉시 개발 금지** — 반복 여부 관찰 후 우선순위 판단 |

## 4. 집중해서 찾을 5가지

| | 무엇 | 왜 중요한가 |
|---|---|---|
| **A** | 멈춘 곳 — "다음에 뭘 해야 하지?" | 흐름이 끊긴 지점 |
| **B** | 불안한 곳 — "잘못되면 어떡하지?" | 기능보다 **실수 가능성에 대한 불안**이 이탈을 만든다(Import 범위 사례) |
| **C** | **기존 도구 복귀 — "그냥 엑셀에서 할게"** | **가장 중요.** 단순 UX가 아니라 제품이 실제 업무를 끊고 있다는 신호 |
| **D** | 이해 못한 용어 | 관찰 대상: 동일인 후보 · 상품행 · 배송그룹 · 일괄 적용 · 변경사항(Draft). 멈추지 않고 넘어가도 **잘못 이해했으면 기록** |
| **E** | 흐름 불일치 | 제품 메뉴 순서 ≠ 실제 업무 순서 → 정보 구조 문제일 수 있음 |

## 7. 경계

**자율**: QA 노후화 · flaky·상태 오염 · 범위 내 제품 버그 · UX 명확화 · 용어 개선 · 안내 추가 · 기존 흐름 연결 개선 · cleanup · baseline 재측정 · 회귀 실행 · 정적/배포 검증.

**금지**: assertion 삭제 · 대상 축소 · sleep으로 억지 PASS · 무한 retry · **발견되지 않은 신규 기능 선제 구현**.

**BLOCKER 4종**(①제품 정책 ②비가역 데이터 ③권한·보안 ④신규 기능/범위 확대)은 `현상 → 재현 → 근거 → 영향 범위 → 선택지`까지만 정리하고 멈춘다.

**수정 후 최소 QA**: 해당 기능 QA + 영역 필수 회귀 + (영향 시) user3/user6 격리 + cleanup baseline diff = 0 + tsc·ESLint·Build·Production·git clean. 제품 화면 구조가 바뀌면 [Landing Product Parity Gate](../qa/STEP13-PHASE-B/REGRESSION-GATE.md#1-1-landing-product-parity-gate-cpo-결정-2026-09-05)도 적용한다.
