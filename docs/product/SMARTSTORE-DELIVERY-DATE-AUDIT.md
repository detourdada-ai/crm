## B. 현재 매핑 — 실제로 무엇이 배송일이 되는가

```
옵션정보 "…/ 날짜 선택: 09월09일"
    ↓  parseDeliveryDateFromOption()   ← 우선 적용
    ↓
배송일 2026-09-09
    ↓
order_shipments.delivery_date   ← ★ 실제 배송 운영 기준
    ↓ (대표값 파생)
orders.delivery_date

[fallback] 매핑된 delivery_date 컬럼(=발송일)  ← 옵션에 날짜가 없을 때만 사용
결제일 → order_date
```

코드상 `const effectiveDate = 옵션에서파싱한날짜 ?? 매핑된배송일 ?? null` 이므로
**옵션 파싱이 먼저다.** 이 파일은 467행 전부 옵션에 날짜가 있어 `발송일` fallback은 **한 번도 쓰이지 않는다.**

## F. ⚠️ 정정 — 내가 왜 틀렸나

앞선 보고에서 **"스마트스토어 주문의 배송일이 파일 받은 날로 일괄 설정되고 있다"** 고 했다.
근거로 두 가지를 들었는데 둘 다 잘못이었다.

1. **`delivery_date ← 발송일` 매핑만 보고 결론을 냈다.** 코드에 옵션 파싱이 **우선 적용**되는
   경로가 있는데 매핑 테이블만 확인하고 실행 경로를 끝까지 따라가지 않았다.
2. **`orders.delivery_date`(대표값)로 대조했다.** 한 주문이 여러 배송일로 쪼개지면 이 값은
   개별 행과 다르다. 그래서 "불일치 35/60"이 나왔고 이를 매핑 오류로 오인했다.
   실제 운영 기준인 `order_shipments.delivery_date`로 대조하면 **120/120 일치**다.
3. 배송일 분포가 업로드 날짜와 겹쳐 보인 것도, 사장님이 **매일 아침 당일 배송분을
   올리기 때문**이지 업로드 날짜가 배송일이 된 것이 아니었다.

이번 STEP22에서 내가 근거 없이 단정한 것은 이번이 **두 번째**다(앞서 "발송일이 있으니
발송처리로 사라졌다"도 무효였다 — 그 역시 `발송일`이 전 행 동일값인 걸 확인하지 않은 탓).
두 번 다 **컬럼 이름만 보고 값을 확인하지 않은 것**이 원인이다. 앞으로 이 영역에서는
**컬럼의 실제 값 분포를 먼저 찍어보고** 결론을 낸다.
