## 1. §9 확인 — 현재 UI로 구분 가능한가? **아니오**

현재 화면의 선택지는 `가져올 주문 범위` 3개다(`column-mapping-form.tsx`).

| 선택지 | 화면 문구 |
|---|---|
| 오늘 주문 가져오기 | "오늘 처리할 주문만 가져옵니다. 매일 주문을 접수하는 경우에 적합합니다." |
| 특정 날짜 주문 가져오기 | "선택한 날짜의 주문만 가져옵니다." |
| 전체 주문 가져오기 | "엑셀에 포함된 누적 주문을 모두 확인합니다." |

그리고 안내 문구는 이렇다.

> "{기준 날짜} 기준으로 오늘에 해당하지 않는 주문은 **등록되지 않고** '날짜 조건 제외'로 별도 집계됩니다."

### 왜 구분에 쓸 수 없는가 — 4가지

#### ① 의미가 다르다 (가장 위험)
현재 옵션은 **"이 파일에서 어떤 행을 등록할지"** 를 정하는 **입력 필터**다.
**기존 주문을 어떻게 할지는 화면 어디에도 없다.**

여기에 "당일 최신화(파일에 없는 기존 주문을 배송 대상에서 제외)"를 얹으면,
**지금까지 '오늘 주문 가져오기'를 써 온 사장님이 아무것도 바꾸지 않았는데
다음 업로드부터 기존 주문이 배송 대상에서 사라진다.** 화면 문구는 여전히
"가져올 범위"라서 예고조차 없다.

#### ② 기준 날짜가 사용자 선택이고, 실제로는 배송일이 아니다
현재 필터 기준은 `주문일 / 배송일 / 발송일` 중 **사용자가 고른다**. CPO 정책은
**배송일 기준**인데, 사장님이 주문일 기준을 고르면 최신화 대상 집합이 정책과 달라진다.
그리고 3번에서 보듯 **스마트스토어의 "배송일"은 실제 배송일이 아니다.**

#### ③ "오늘"과 "선택 배송일"이 다르다
`today` 모드는 **업로드하는 시점의 오늘**이다. 9/8 아침에 9/9 배송분을 미리 올리는
누적형 운영과 어긋난다. 실제로 user2 주문의 배송일 분포에 **2026-09-09가 19건** 있다 —
미래 배송일 주문이 실재한다.

#### ④ §13 STOP 조건에 직접 해당
지시서 §13의 **"기존 주문의 상태를 새로운 방식으로 변경해야 함"** 이 바로 이 동작이다.

## 2. ⚠️ 이전 보고 정정 — "발송처리로 사라졌다"는 근거는 무효였다

`docs/product/STEP22-CANCEL-IMPACT-STUDY.md`와 STEP22-2 리포트에서 이렇게 보고했다.

> "조회기간 안인데 사라진 207건의 `발송일`을 확인한 결과 **100% 발송일 있음** →
> 전부 발송처리가 끝나서 목록에서 빠진 것이다."

**이 근거는 성립하지 않는다.** 다시 확인한 결과:

```
파일 467행 중 발송일 값이 있는 행: 467 (전부)
사라진 건 발송일 종류: 1가지
유지된 건 발송일 종류: 1가지   ← 값이 서로 같다
샘플: 사라진 건 발송일 46272.3313 / 유지된 건 발송일 46272.3313
```

**`발송일`은 행마다 다른 값이 아니라 파일 전체에 같은 값 하나가 찍혀 있다.**
그 값(46272.3313)을 환산하면 **2026-09-07 07:57** — 파일명
`..._20260907_0757.xlsx`의 **내려받은 시각과 정확히 일치**한다.

즉 사라진 건과 유지된 건의 발송일이 동일하므로 **이 컬럼으로는 아무것도 구분할 수 없다.**
"발송처리 완료라서 빠졌다"는 제 결론은 **근거 없이 내린 것**이었다. 사라진 진짜 이유는
여전히 확인되지 않았다.

> 다행히 CPO가 누락 기반 자동취소를 폐기하기로 결정해 이 오판이 제품에 들어가지는 않았다.
> 관련 문서의 해당 서술은 이 문서로 정정한다.

## 3. 🔴 새로 발견한 실제 문제 — 배송일이 "파일 받은 날"로 들어가고 있다

user2의 실제 import 매핑을 확인했다.

| 파일 | order_date ← | delivery_date ← |
|---|---|---|
| 스마트스토어 20260908 | 결제일 | **발송일** |
| 스마트스토어 20260907 | 결제일 | **발송일** |
| 주문한장 표준템플릿 | 주문일시(결제일) | 배송일 |

자동 매핑기의 `delivery_date` 별칭에 `발송일`이 포함되어 있고, 스마트스토어 파일에는
`발송일`과 `배송희망일`이 둘 다 있는데 **`배송희망일`은 467행 전부 비어 있고 `발송일`만
채워져 있다.** 그래서 `발송일`이 배송일로 매핑된다.

**그런데 2번에서 확인했듯 `발송일`은 파일을 내려받은 시각이다.**

→ **스마트스토어로 등록된 주문의 배송일이 "그 파일을 받은 날"로 일괄 설정되고 있다.**

user2의 배송일 분포가 이를 뒷받침한다.

```
2026-08-31: 116건   2026-09-02: 77건   2026-09-04: 68건
2026-09-03:  51건   2026-09-07: 39건   2026-09-09: 19건
```

이 날짜들은 user2가 **실제로 업로드한 날짜와 일치**한다(8/31, 9/2, 9/3, 9/4, 9/7, 9/8).
배송일이 주문의 성격이 아니라 **업로드 행위의 부산물**이 되어 있다.

### 왜 이번 정책에 결정적인가
CPO 정책의 핵심은 **"선택한 배송일의 주문을 최신본으로 본다"** 이다.
그런데 그 배송일이 실제 배송일이 아니라 파일 다운로드 시각이면,
**"9/8 배송분 최신화"가 실제로는 "9/8에 내려받은 파일로 등록된 주문 최신화"** 가 된다.
정책이 의도한 것과 다르다.

**이건 STEP22 범위를 넘는 별도 사안**이므로 임의로 고치지 않았다.
