## 0. 이 문서가 답하는 질문

> **주문:한장은 누구의 이름으로 카카오톡 메시지를 보내는 플랫폼인가?**

## 1. 5개 질문 — 공식 문서 확인 결과

| # | 질문 | 결과 | 근거 |
|---|---|---|---|
| 1 | 한 계정/API Key에서 **여러 발신프로필** 등록·발송 가능? | **가능(문서 근거 있음)** | 알리고 API에 **`POST /akv10/profile/list/` — "등록된 카카오채널 리스트"** 조회가 존재한다. 채널 목록이라는 개념 자체가 계정당 다수 채널을 전제한다. 발송 시 `senderkey`를 요청마다 지정하므로 호출 단위로 발신프로필을 바꿀 수 있다 |
| 2 | **소유 사업자가 다른** 채널을 우리 계정에 붙일 수 있나? | **문서로 확인 불가 → 문의 필요** | 발신프로필 등록은 `profile/auth`(카카오채널 인증) → `category` → `profile/add`(심사) 순서인데, **인증 단계에서 누구의 채널 관리자 권한이 필요한지**가 문서에 없다. 채널 소유권·사업자 정보 귀속이 걸린 문제 |
| 3 | 충전 주체와 **테넌트별 가상 잔액(Ledger)** | **알리고 잔액은 계정 단위 — 테넌트 분리는 우리가 해야 한다** | 잔액 조회 `POST /akv10/heartinfo/`가 **계정의 잔여 발송 건수**(`ALT_CNT`/`SMS_CNT`/`LMS_CNT`)를 돌려준다. 발신프로필별 잔액 개념이 문서에 없다 → 우리가 대량 충전하고 **테넌트별 Ledger는 주문:한장 내부에서 관리**하는 구조가 필연 |
| 4 | 알림톡 / 브랜드메시지(친구톡) 콘텐츠 범위 | **확인됨(아래 표)** | `alimapi.html`, `friendapi.html` |
| 5 | 대행 발송·재판매 계약 조건 | **문서에 없음 → 문의 필요** | 알리고 사이트에 대리점/재판매/고객사별 과금 정책 기재 없음. 고객센터(cs@alipeople.kr) 확인 필요 |

### 1-1. 질문 4 상세 (추측 없이 문서 기재값만)

| 기능 | 알림톡 | 브랜드메시지(친구톡) |
|---|---|---|
| 텍스트 | 가능(최대 1,000자) | 가능 |
| 이미지 | 문서에 별도 규격 기재 없음 | **가능** — IMAGE/WIDE `800x400`(가로 500 이상), WIDE_ITEM_LIST 메인 `800x400`·서브 `800x600` |
| 버튼 | 템플릿에 포함(승인 대상) | **6종** — 채널추가(AC) / 배송조회(DS) / 웹링크(WL) / 앱링크(AL) / 봇키워드(BK) / 메시지전달(MD) |
| 웹 링크 · 앱 링크 | 템플릿 승인 범위 내 | WL / AL로 지원 |
| 캐러셀·영상 | 없음 | 지원(CAROUSEL 등 템플릿 유형) |
| 광고/마케팅 | **불가**(정보성 알림 전용) | **가능** — `advert_yn` 광고분류 필드가 있고 **기본값 Y** |
| 템플릿 사전 승인 | **필수** — 조회/등록/수정/**검수요청** API 존재, `tpl_code`로 발송 | 템플릿 유형 선택 방식(사전 승인 절차는 문서에 별도 기재 없음) |

> **제품 원칙과 직결**: 배송 알림은 알림톡(정보성), 신메뉴·행사는 브랜드메시지(광고). 둘은 **비용도 정책도 다른 경로**이므로 STEP15-B에서 `MessageKind`를 분리해 둔 것이 맞았다. 수신거부 안내 의무는 문서에 명시가 없어 **정책 확인 필요 항목**으로 남긴다.

## 2. 모델 비교표

| 항목 | **A. 우리 계정(단일 발신프로필)** | **B. 사장님별 알리고 계정** | **C. 플랫폼 계정 + 테넌트별 발신프로필** |
|---|---|---|---|
| 사장님 가입 난이도 | **가장 낮음** — 아무 것도 안 해도 됨 | **가장 높음** — 알리고 가입·채널 개설·템플릿 승인 직접 | 중간 — 카카오 채널만 준비, 연결은 우리가 |
| API Key 관리 | 우리 키 1세트 | **테넌트마다 키 3개 보관** (유출 시 피해 큼) | 우리 키 1세트 + 테넌트별 `senderkey` |
| senderkey | 1개(주문:한장 채널) | 사장님 각자 | **테넌트별**(가게 채널) |
| 충전 | 우리가 대량 충전 | 사장님이 각자 | 우리가 대량 충전 |
| 테넌트별 과금 | 내부 Ledger 필요 | 불필요(각자 결제) | **내부 Ledger 필요** |
| 우리 수익화 | 가능(원가-청구 차액) | **어려움**(우리를 안 거침) | 가능 |
| 보안 | 좋음(키 1세트) | **나쁨**(타사 키 다수 보관) | 좋음 |
| MVP 적합성 | **높음** | 낮음 | 중간(질문 2 답에 종속) |
| 장기 SaaS 적합성 | **낮음** — 고객이 "주문:한장"에서 온 메시지를 받는다 | 중간 | **높음** — "○○반찬"에서 온 메시지 |

### 치명적 차이 하나
고객이 받는 메시지의 **발신자 이름**이다.

```
A:  [주문:한장]  배송이 시작되었습니다     ← 고객은 이 브랜드를 모른다
C:  [○○반찬]    배송이 시작되었습니다     ← 사장님의 브랜드
```

배송 알림은 **가게와 고객 사이의 대화**다. A로 시작하면 나중에 C로 옮길 때
발신프로필·템플릿을 전부 새로 만들고 재승인받아야 한다(마이그레이션 비용).

## 3. 권장

- **MVP 권장 모델: C (조건부) → 확인 불가 시 A**
  질문 2(타 사업자 채널을 우리 계정에 연결 가능한가)의 답이 **가능**이면 처음부터 C로 간다.
  코드는 이미 준비돼 있다 — `senderkey`를 환경변수가 아니라 **테넌트 설정에서 읽도록** 바꾸면 되고,
  `MessageProvider` 인터페이스 뒤라 제품 로직은 바뀌지 않는다.
  답이 **불가/불명확**이면 A로 베타를 시작하되, **템플릿을 최소화**해 나중에 C로 옮길 때 재승인 부담을 줄인다.

- **장기 확장 모델: C**
  가게 브랜드로 나가고, 우리는 잔액·정산·템플릿을 대신 운영하는 구조. 이것이 "주문 → 배송 → 알림 → 고객 데이터"가
  한 SaaS 안에서 이어진다는 제품 전략과 맞는 유일한 모델이다.

- **B는 제외 권장.** 사장님이 알리고에 직접 가입해야 하는 순간 "엑셀을 줄여주는 도구"를 쓰러 온 사람의 진입 장벽이
  과해지고, 우리가 타사 API Key를 대신 보관하는 보안 부담까지 생긴다.

## 4. 알리고에 확인해야 할 문의 (그대로 보내면 되는 형태)

1. 하나의 알리고 계정(apikey/userid)에 **여러 개의 카카오 발신프로필(senderkey)** 을 등록해 운영할 수 있습니까? (`/akv10/profile/list/`가 있는 것으로 보아 가능해 보이는데 정책상 제한이 있습니까?)
2. 그 발신프로필들의 **소유 사업자가 서로 다른 경우**(플랫폼이 고객사 채널을 연결)도 허용됩니까? 필요한 서류·권한은 무엇입니까?
3. 포인트 충전은 계정 단위만 가능합니까? 발신프로필(고객사)별로 잔액을 분리할 수 있습니까?
4. SaaS가 고객사를 대신해 발송하고 **고객사별로 과금(재판매)** 하는 것이 약관상 허용됩니까? 별도 계약이 필요합니까?
5. 알림톡 템플릿 **검수 신청 주체**는 계정 소유자입니까, 발신프로필 소유자입니까?

## 5. 사장님 메시지 설정 — 필요한 정보 설계 (DB 변경 없음)

모델이 확정되기 전이라 **스키마를 만들지 않는다.** 현재 `app_settings`의 `message_settings:<username>`에
담을 수 있는 범위로만 정리한다.

```
[기본]      상호명 · 사업자명 · 담당자
[카카오]    채널명 · 채널 URL · 발신프로필 상태(none/pending/ready)
[발송]      senderkey(모델 C에서만) · 사용 가능 상태 · 승인 상태
[잔액]      현재 잔액 · 최근 충전 · 잔액 부족 시 발송 중지 여부
```

모델 A면 `senderkey`가 플랫폼 공용이라 테넌트 설정에서 빠지고, C면 필수가 된다.
**이 차이 때문에 지금 컬럼을 만들면 두 번 만들게 된다.**

## 6. 선충전 · 발송 동의 구조 초안 (구현 없음)

**자동 알림과 수동 발송을 분리한다.**

| | 자동 배송 알림 | 수동 공지 / 마케팅 |
|---|---|---|
| 동의 시점 | **최초 설정 시 1회** — "자동 발송이 발생하면 잔액에서 건별 차감됩니다"에 동의 | **매 발송 직전** |
| 발송 전 표시 | 설정 화면에 예상 단가·현재 잔액 | 대상 수 · 발송 가능 수 · 예상 차감 · 발송 후 잔액 |
| 확인 버튼 | 없음(매번 물으면 자동화 의미가 사라진다) | **[1,248명에게 발송하기]** 명시적 클릭 |
| 잔액 부족 | 발송 중지 + `skipped(INSUFFICIENT_BALANCE)` 기록 | 발송 자체를 시작하지 않음 |

`message_log`에 `provider_cost` / `platform_fee` / `tenant_charge` / `balance_before` / `balance_after`가
이미 있으므로, Ledger가 붙어도 **로그 스키마는 다시 바꾸지 않아도 된다.**

## 7. 무분별한 광고 방지 — 정책 초안 (자동 차단 기능은 만들지 않음)

| 구분 | 성격 | 자동 발송 |
|---|---|---|
| 운영 메시지 | 배송 예정·시작·완료, 주문 안내 | **허용** (고객의 실제 주문과 직접 연결) |
| 고객 관계 | 휴무·배송 일정 변경·명절 안내 | 수동만 |
| 마케팅 | 신메뉴·할인·정기배송 모집 | **자동 금지** — 수신 동의·친구 여부·광고 표기(`advert_yn`) 필요 |

구조적 차단은 이미 코드에 있다 — 자동 이벤트는 `MessageKind = "delivery_notice"` 하나만 사용하고,
마케팅은 dispatch 경로에 연결되어 있지 않다. **주문:한장이 "카카오 대량 발송기"가 되지 않게 하는 것은
기능 제한이 아니라 구조로 막는다.**

## 8. STOP 보고

| | 조건 | 상태 |
|---|---|---|
| STOP 1 | 멀티 발신프로필 구조가 불가능하거나 정책 불명확 | **부분 발생** — 계정당 다중 채널은 API 구조상 가능해 보이나(§1-1), **타 사업자 채널 연결 가능 여부는 문서에 없음** |
| STOP 2 | 재판매/재과금에 별도 계약·법적 조건 필요 | **발생** — 알리고 공식 문서에 대행·재판매 정책 기재 없음. 문의 필요 |
| STOP 3 | 사장님별 API Key가 강제됨 | 미발생(현재 근거로는 강제되지 않음) |
| STOP 4 | 현재 개인정보/수신동의 구조로 마케팅 발송 불가 | **주의** — 브랜드메시지는 `advert_yn` 광고 분류가 기본 Y이고 수신 동의 개념이 필요한데, 우리 제품에는 **고객 광고 수신 동의 필드가 없다**. 배송 알림(정보성)에는 영향 없음 |

**따라서 모델 최종 확정은 알리고 문의(§4) 회신 후에 한다.** 그 전에 실제 API를 붙이면
발신프로필·템플릿을 다시 만들 위험이 있다.
