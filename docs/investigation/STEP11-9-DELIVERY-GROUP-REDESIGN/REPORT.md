## 2. 현재 100m 알고리즘 완전 조사

### A. 그룹 생성 기준
- 위치: `src/lib/services/delivery-group-regeneration.service.ts` (orchestration) + `src/lib/services/spatial-grouping.service.ts`(순수 클러스터링 함수).
- 반경: `GROUP_RADIUS_METERS = 100`(상수, `delivery-group-regeneration.service.ts:7`) — 설정값이 아니라 코드 상수. DB 스키마(`delivery_groups.radius_meters`)에는 값이 저장되지만 실제로 이 상수 외의 값을 읽어오는 경로는 없다(컬럼은 있지만 미사용).
- 기준: **주문 간 실거리(Haversine) ≤ 100m면 연결**, 격자 아님. 최소 그룹 크기 2(1건은 미그룹).
- **연쇄 연결 확인됨(중요)**: `clusterPointsByDistance`는 Union-Find로 connected-component를 구성한다. A-B가 80m, B-C가 80m면 A-C 직선거리(160m, 100m 초과)와 무관하게 하나의 그룹이 된다 — CPO가 예상한 그대로다. 이번 조사에서도 08-27 그룹#7(14건)처럼 체인 연결로 커진 그룹이 실제로 존재한다.

## 7. 좋은/나쁜 사례

숫자 튜닝(반경만 키우기)이 왜 답이 아닌지 사례로 확인된다.

**[좋게 개선된 사례] — 이번 조사에서 발견된 유일한 "단지 분리" 실제 사례**
```
꿈동산신안아파트, 2026-08-27, 3건
기존(100m): 2개 그룹으로 쪼개짐
단지 우선 모델(B/C/D): 1개 그룹으로 정상 통합
```
→ **8일 396건 중 "동일 단지인데 100m 밖이라 분리된" 사례는 정확히 이 1건뿐이었다.** 즉 지오코딩 좌표가 갈라지는 문제(같은 아파트인데 200m 이상 차이)는 이번 데이터 범위에서는 CPO가 우려한 만큼 광범위하지 않았다 — 대부분의 동일 단지 주문은 이미 좌표가 거의 동일(0m, 같은 건물 좌표로 지오코딩됨)해서 100m 안에서 자연스럽게 뭉친다.

## 8. 그룹 이름 설계 가능성

기존 데이터만으로 사람이 읽을 수 있는 이름 생성이 이미 가능함을 확인:
- **동일 단지 그룹**: `{추출된 건물명} · {건수}건` — 이미 `buildGroupBuildingLabels`가 하는 방식 그대로, 모델 B/C/D 결과에도 동일 적용 가능(스크립트에서 `"고덕그라시움아파트 · 9건"` 형태로 실제 생성 확인).
- **건물명 없는 근접 그룹**: `{구성원 다수결 읍면동} 인근 · {건수}건` — 기존 `representativeRegion`의 다수결 로직 재사용, 외부 API 불필요. 스크립트에서 `"망월동 인근 · 4건"` 형태로 실제 생성 확인.

## 9. 종합 판단

1. **미분류율(커버리지 부족)이 "동일 단지 분리"보다 훨씬 큰 문제다.** 8일 평균 커버리지가 현재 36.3%에 불과하다 — 이건 반경 문제가 아니라 애초에 그룹 후보 자체가 2건 미만인 경우(주문이 넓게 퍼져 있음)가 많기 때문이다. 어떤 모델을 쓰든(B 제외) 이 숫자를 극적으로 올리려면 반경을 키워야 하는데, 그러면 건물 혼합이 동반 폭증한다 — 근본적 트레이드오프다.
2. **"단지 우선" 로직 자체는 실측으로 효과가 검증됐다.** 같은 반경(100m)에서 건물 혼합 건수가 13건→10건으로 줄고, 동일 단지 분리 사례(1건)를 정확히 해결한다 — 부작용 없이 순수 이득.
3. **B(단지전용 단독)는 채택 불가.** 커버리지가 오히려 현재보다 낮다(21.5%) — 단독주택/빌라/상가 등 건물명이 안 뽑히는 주문이 절반 이상이라 이 모델만으로는 그 주문들이 전부 미분류로 남는다.
4. **"동 경계 유지"(D)가 "동 경계 허용"(C)보다 명백히 우월하다.** 같은 반경에서 동 혼합을 정확히 0으로 만들고, 건물 혼합/커버리지는 거의 동일하거나 더 낫다(D-300 건물혼합 27 vs C-300 27, 동일 — 하지만 동혼합은 0 vs 5). 손해가 없으므로 동 경계는 유지하는 쪽이 항상 낫다.

## 10. 권고

**Option 1(동일 단지 우선 + 건물 없는 주문만 거리 기반, 반경은 현행 100m 유지)을 권고한다.**

근거:
- CPO가 예상한 대로 "좌표는 절대 기준이 아니라 주소 정보가 부족할 때의 보완 수단"이라는 구조가 데이터로 뒷받침된다.
- 유일하게 실측된 "동일 단지 분리" 사례(1건)를 정확히 해결하면서, 반경을 그대로 100m로 유지하므로 A-200/300/500에서 확인된 건물 혼합 폭증 위험을 전혀 지지 않는다.
- Option 2(동일 단지 + 동일 읍면동 내부 근접도, 즉 D 계열)는 반경을 키울 때(200~300m)만 의미가 있는데, 반경을 키우는 순간 "미사강변 OO" 계열처럼 이름이 비슷한 별개 단지가 반복적으로 섞이는 문제가 3일 연속 재현됐다 — 커버리지 이득(36%→49~51%) 대비 리스크가 더 크다고 판단한다. 다만 이 옵션은 완전히 배제할 필요는 없고, "반경을 키우고 싶다면 반드시 동 경계를 유지한 채로만"이라는 조건부 대안으로 남겨둔다.
- Option 3(좌표 알고리즘 자체 개선, 예: PostGIS/DBSCAN 등)은 이번 데이터로는 근거가 없다 — 문제의 본질이 "알고리즘 정확도"가 아니라 "좌표만 보고 있다"는 입력 데이터 설계이므로, 알고리즘을 정교하게 바꿔도 건물명을 안 쓰는 한 같은 트레이드오프가 반복된다.
- Option 4(그룹 기능 자체의 활용도가 낮아 다른 방향 권고)는 STEP11-8의 미분류율 문제와 이번 커버리지 36%를 보면 일리가 있지만, 이번 조사로 "그룹 정의를 바꾸면 최소 하나의 실제 문제(단지 분리)는 부작용 없이 고칠 수 있다"는 게 확인됐으므로, 기능을 접기보다 Option 1 수준의 최소 개선부터 시도할 근거가 있다고 본다.

**이번 Gate에서 확정/구현하지 않음** — 코드/DB/UI 전혀 변경하지 않았고, 위 권고는 CPO 판단을 위한 자료다. STEP11-8에서 이미 나온 "그룹을 화면에 어떻게 노출할지"(안 A/B/C) 판단은 이번 결과와 별개로 CPO가 종합해서 결정할 사안이다.
