## 1. 원인 (한 문장)

> 저장 로직이 아니라, **드롭 직후 수백 ms 안에 날아간 "변경사항 저장" 첫 클릭이 삼켜져
> 서버 액션(`reorderShipmentsAction`)이 아예 호출되지 않은 것**이다.

## 2. 원인 확정 근거 — 성공/실패 대조 계측

Production에서 실패를 재현하며 `Drag → local order → 배너 → 클릭 → 서버액션 POST →
DB UPDATE → route_order 재조회` 각 단계를 계측했다.

| 단계 | 성공 케이스 | 실패 케이스(3/3 동일) |
|---|---|---|
| 드래그 → 화면 순서 변경 | 뒤바뀜 | **뒤바뀜(동일)** |
| "변경사항 N건" 배너 | 2건 | **2건(동일)** |
| 저장 버튼 상태 | enabled | **enabled(동일)** |
| 클릭 후 버튼 라벨 | `(사라짐)` | **`변경사항 저장` 그대로** — 저장 트랜지션이 시작조차 안 됨 |
| 클릭 후 배너 | `(사라짐)` | **`변경사항 2건` 그대로** |
| **서버액션 POST(`next-action` 헤더)** | **1건** | **0건** |
| 클라이언트 JS 오류 | 없음 | **없음** |
| 저장 토스트 | `2건 저장했습니다.` | **없음** |
| DB `route_order` (20초 폴링) | 뒤바뀜 | **R1=1, R2=2 그대로** |
| **같은 버튼 재클릭** | — | **POST 1건 → 즉시 정상 저장** |

**해석**: 핸들러는 정상적으로 연결돼 있다(재클릭하면 항상 저장됨). 서버·DB·저장 로직은
무관하다(요청 자체가 나가지 않음). 클릭 전에 800ms만 기다리자 6/6 PASS로 바뀌었다 —
드롭 직후 극히 짧은 구간의 첫 클릭만 소실된다. 사람이 드래그 핸들에서 저장 버튼까지
포인터를 옮기는 데 걸리는 최소 시간보다 짧은 구간이라, 자동화 테스트가 사람보다
빨리 눌러서 드러난 현상이었다.

**교차 검증**: 1차 20사이클 실행에서 행 D&D는 100/100 PASS였고, 대기를 넣지 않았던
**그룹 D&D 구간만 같은 양상으로 실패**(저장 토스트 없음 + 순서 미반영)했다. 동일 원인이
다른 구간에서 재현된 것으로, 원인 판정이 역으로 확인됐다.

## 3. 수정

### 3-1. 제품 — `src/lib/repositories/order-shipments.repository.ts` `reorderForDriver()`
이번 증상의 직접 원인은 아니지만, 조사 중 **저장이 조용히 사라질 수 있는 실제 결함**을
발견해 함께 고쳤다.

- **문제**: `route_order`를 배송건마다 개별 UPDATE로 `Promise.all` 발사하면서 **각
  UPDATE의 `error`를 한 번도 확인하지 않았다.** 일부/전부가 실패해도 함수는 정상
  반환했고, 상위 `reorderShipmentsAction`은 `ok`를 돌려주며 화면엔 "N건 저장했습니다"
  토스트까지 떴다.
- **수정**: 같은 파일의 **배정 경로가 이미 쓰고 있는** `bulk_update_shipment_route_order`
  RPC(마이그레이션 0046)로 통일. 단일 UPDATE 문 1개라 부분 실패가 구조적으로 생기지
  않고, 실패하면 throw되어 사용자에게 오류가 보인다.
- **제약 준수**: `route_order` 그대로 / `reorderShipmentsAction` 그대로 / 새 reorder 시스템
  없음 / 새 DB 컬럼·마이그레이션 없음 / 그룹 D&D 로직 미변경 / 배정필요 D&D 구조 미변경.
  결과적으로 **배송중과 배정필요가 동일한 저장 경로**를 타게 됐다.

### 3-2. QA — `scripts/qa/step12-11-delivery-ui-cleanup.ts`
- 행 D&D 검증을 `runRowReorderCycle()`로 묶어 **양방향(순서1→2, 2→1)·연속 변경**을
  같은 코드로 반복한다. `R23_ROW_REPEAT`로 횟수 지정(기본 1).
- 사이클마다 **시작순서 → 배너 → 저장 전 화면순서 → DB `route_order` → 새로고침 유지**
  5가지를 모두 검증한다(기존엔 화면만 보고 통과할 수 있었다).
- 클릭 전 대기(800ms)를 행/그룹 두 구간에 동일 적용 — 결함 마스킹이 아니라 **실제 사용자
  조작 속도를 반영**하는 것이며, 그 근거를 코드 주석에 남겼다.
