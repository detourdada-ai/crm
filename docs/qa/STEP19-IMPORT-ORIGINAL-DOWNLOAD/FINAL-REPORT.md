## 1. 사전 조사 — 원본은 저장되고 있지 않았다

지시서의 A/B 분기 중 **B**였다. 4중으로 확인했다.

1. `imports` 실제 컬럼에 경로·본문이 없음 (`file_name`은 이름 문자열뿐)
2. Supabase Storage 버킷 목록 `[]` — 버킷 자체가 0개
3. 코드베이스 전체에 `storage.from(` / `.upload(` / `fs.writeFile` 0건
4. `analyzeImportFileAction`에서 `file.arrayBuffer()` → 파싱 후 **바이트가 요청과 함께 소멸**

그래서 "다운로드 버튼만 추가"는 불가능했고, 보관 구조부터 만들었다.

## 2. 구현

```
사장님 업로드 → 파싱/등록(기존 그대로)
              → 확정 시점에 원본을 private 버킷에 보관
              → imports.file_path에 경로 연결
Admin        → 이력 화면의 [원본 다운로드]
```

- 버킷 `import-originals` (public=false), 경로 `{tenant_id}/{uuid}.{ext}`
- `imports.file_path text nullable` — 기존 행은 null 유지, **과거 업로드 소급 복구 없음**(원본이 애초에 없다)

### 판단한 지점 3가지

1. **원본은 "등록 확정" 시점에만 보관한다.** 분석 단계에서 저장하면 매핑 화면에서
   되돌아간 파일까지 쌓인다 — 아무도 참조하지 않는 개인정보 파일을 남기지 않기 위해,
   확정 시 브라우저가 파일을 한 번 더 보내도록 했다.
2. **보관 실패로 주문 등록을 실패시키지 않는다**(best-effort, `file_path=null`로 남고 등록은 진행).
   이건 운영/테스트 지원 기능이지 사장님 업무의 일부가 아니다 — `saveColumnMapping`과 같은 판단.
3. **서명 URL을 브라우저로 내보내지 않았다.** 서버가 service-role로 바이트를 읽어 흘려주고
   `Cache-Control: no-store`를 건다. 지시("파일 URL을 DB에 그대로 노출하지 않음")보다 한 단계 더 잠갔다.
   라우트는 **조회보다 권한 체크를 먼저** 해서 403/404 차이로 "그 import가 존재한다"는 사실도 흘리지 않는다.

## 4. 보안/권한 — Storage 격리 7/7 PASS

앱 권한 체크만 믿지 않고 **버킷 자체가 잠겨 있는지**를 따로 검증했다
(`scripts/qa/step19-import-original-storage-isolation.ts`).

```
PASS  버킷이 존재하고 private이다 (public=false)
PASS  service_role로 업로드·다운로드되고 내용이 같다
PASS  anon 키로는 다운로드가 차단된다 — Object not found
PASS  anon 키로는 목록이 보이지 않는다 — 0건
PASS  public URL 직접 호출이 차단된다 — HTTP 400
```

버킷에 storage 정책을 **하나도 만들지 않았다** — 따라서 브라우저에 노출되는 anon 키로는
읽기·목록·직접 URL이 전부 차단되고, RLS를 우회하는 service_role(서버 코드)만 접근한다.

## 5. 검증 중 발견해 고친 것 — 이력 삭제 시 원본이 남았다

첫 회귀 실행 후 버킷에 **orphan 3건**이 남은 것을 발견했다.

- **현상**: 이력 삭제가 `imports` 행만 지우고 storage 오브젝트는 그대로 뒀다.
- **왜 심각한가**: 사장님이 업로드 이력을 삭제해도 **고객 이름·주소·연락처가 든 원본이
  버킷에 남고**, 참조하는 행이 사라져 아무도 그 존재를 알 수 없게 된다. 개인정보 파일에
  대해 가장 나쁜 형태다.
- **분류**: A(내가 새로 만든 경로의 버그) — 자율 수정 범위.
- **수정**(`79191f6`): `deleteImport`(단건/전체삭제 공용)와 `tenant-reset` 양쪽에서 행 삭제 전에
  `file_path`를 읽어두고 오브젝트까지 제거한다. 파일 정리 실패로 이력 삭제 자체를 되돌리지는
  않는다(사장님 입장에서 "삭제가 안 되는" 더 나쁜 상태가 되므로) — 대신 로그로 추적한다.
- **회귀 고정**: E2E에 T15로 박았다.

이어서 회귀를 다시 돌리자 orphan이 **1건 더** 생겼는데, 이번엔 제품이 아니라 QA 스크립트가
`imports` 행을 service-role로 직접 지워 제품 경로를 타지 않은 것이었다 — 스크립트 쪽을
고쳤다(`866c24f`).
