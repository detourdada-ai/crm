## 1. 적용한 정책

| 대상 | 기간 | 동작 |
|---|---|---|

- 안내 문구: 사장님 화면 이력 카드에 `엑셀 등록 이력은 최근 7일만 확인할 수 있습니다.`

  여전히 노출하지 않고 서버가 바이트를 대신 흘려주는 현재 구조 그대로다.

### cron 위치
기존 `beta-expiration`에 섞지 않고 **신규 `/api/cron/import-retention`** 을 만들었다
(`vercel.json`, 매일 18:30 UTC = 03:30 KST). 그쪽은 "메일을 한 번 보낸다"는 알림 잡이고
이쪽은 "데이터를 지운다"는 파기 잡이라, 한쪽 실패가 다른 쪽을 막으면 안 되기 때문이다.
인증은 기존과 동일하게 `Authorization: Bearer $CRON_SECRET`만 통과시킨다.

## 2. 삭제 순서 — 이 구현의 핵심

CPO 지시: *"Storage 삭제 실패 시 DB 이력만 먼저 삭제해서 원본을 잃어버리는 식의 처리는 하지 마세요."*

**Storage 원본을 먼저 지우고, 성공한 건만 이력 행을 지운다.**

반대 순서로 하면 행이 지워진 뒤 파일 삭제가 실패했을 때 **그 파일을 가리키는 참조가
세상에서 사라진다** — 고객 이름·주소·연락처가 든 엑셀이 버킷에 영원히 남고 아무도 존재를
알 수 없다. 개인정보 파일에 대해 가장 나쁜 결과다.

지금 순서의 최악 시나리오:

| 실패 지점 | 결과 | 회복 |
|---|---|---|
| 파일 삭제 실패 | 행을 남긴다(둘 다 존재 = 정합) | 다음 날 재시도 |
| 파일 삭제 성공 후 행 삭제 실패 | 파일 없는 행이 하루 남음 | Admin이 눌러도 404, 다음 실행에서 행 삭제(remove는 멱등) |

**참조 없는 개인정보 파일은 어느 경우에도 생기지 않는다.** 재시도로 남겨둔 건수는
응답의 `deferred`로 관측된다.

## 3. 주문 데이터는 지우지 않는다 (해석 명시)

지시는 "이력 + 원본 파일 자동 삭제"였다. **주문/고객은 지우지 않는 것으로 해석했다** —
보관기간이 끝났다고 사장님의 실제 주문을 지우는 것은 명백히 의도가 아니다.

`orders.import_id`와 `customers.created_by_import_id`가 전부 `on delete set null`이라
이력 행만 지우면 **연결만 끊기고 주문·고객 데이터는 그대로 남는다.** 주문까지 지우는
수동 삭제 경로(`deleteImport`)와 저장소 함수를 분리해 두었다(`deleteRowsOnly`) — 두 경로가
섞이면 크론이 30일 지난 주문을 지우는 사고가 난다.

## 5. 검증 중 발견해 고친 것 — Admin이 30일치에 도달하지 못했다

T4가 처음에 실패했다. 원인은 7일 필터가 아니라 **목록 상한 20건**이었다.

- **현상**: Admin은 전 테넌트를 한 목록에서 보는데 상한이 20건이라, 10일 된 이력이
  21위로 밀려 화면에서 사라졌다(당시 전체 20건 + 시드 2건).
- **왜 중요한가**: 사업장이 몇 곳만 돼도 최근 며칠치로 20건이 차버린다. 그러면
  **원본을 30일 보관하기로 한 정책이 화면에서 무력화된다** — 파일은 있는데 닿을 수 없다.
- **분류**: B(제품 의도가 명확한 범위 내 수정) — 새 정책이 필요 없다.
- **수정**(`419d10e`): Admin 상한을 200으로. 보관기간이 30일로 상한이 잡혀 있으니 목록도
  그 범위를 덮게 했다. 사장님 화면은 7일치라 20건 그대로. 화면 문구도 하드코딩된
  "최대 20건"이 아니라 실제 값을 쓰도록 정리했다.
