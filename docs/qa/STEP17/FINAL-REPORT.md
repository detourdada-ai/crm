## 1. 직접수령 정책 수정 — 완료 (①+②)

### 바꾼 것
| | |
|---|---|
| ① 전환 즉시 정리 | `setFulfillmentMethod(direct_pickup)`에 **`delivery_group_id: null`** 추가 |
| ② 재계산 제외 | `findEligibleForGrouping`에서 **`direct_pickup` 제외** |
| ③ 재계산 트리거 | `setFulfillmentMethodAction`에서 해당 (tenant, 배송일) **그룹 재계산 호출** |

①만 하면 다음 재계산이 도로 끌어들이고, ②만 하면 전환 직후가 정리되지 않습니다. **한 쌍**입니다.
③이 없으면 남은 건들의 건수·중심 좌표가 낡은 채로 남습니다 — 지금까지 재계산은 주문
생성/수정/삭제에서만 돌았고 **배송방식 전환은 그룹에 반영되지 않았습니다.**

### 왕복 검증 중 발견한 결함 1건 (함께 수정)
> **"직접수령 해제" 메뉴가 화면에 있는데 실제로는 동작하지 않았습니다.**

직접수령이 상태를 `완료`로 만드는데, 같은 함수의 UPDATE가 완료 건을 통째로 제외
(`.neq('delivery_status','완료')`)하고 있어 **해제는 언제나 0건**이었습니다.
해제 경로는 완료 제외 대신 **`fulfillment_method='direct_pickup'`인 건에만** 적용하도록
바꿨습니다 — 이 조건이 없으면 **진짜 배송완료 건이 '배송대기'로 되살아납니다.**
해제 시 `배송대기` + `completed_at=null`로 되돌리고, 그룹은 재계산에 맡깁니다
(주소가 바뀌었을 수 있어 옛 그룹으로 되돌리지 않습니다).

## 4. 병목 원인 분류

| 분류 | 판정 | 근거 |
|---|---|---|
| **A. Vercel ↔ DB 지역** | **주원인** | 거의 아무 일도 안 하는 GET(F1/F3)조차 **TTFB 1.1~1.2초**. DB 자체 왕복은 109ms. 즉 **쿼리가 느린 게 아니라 왕복이 먼 것** |
| **D. 순차 처리** | **2순위** | F2 서버 1,684ms − F1 서버 1,174ms ≈ **500ms**. 저장 경로에만 붙는 추가 비용 = 순차 DB 왕복 몇 회분 |
| **C. API round trip** | 관련 | 응답 다운로드 **933ms**. 보드 RSC 페이로드가 커서 재렌더 결과를 통째로 내려받음 |
| **B. DB query** | **아님** | 직접 왕복 109ms, 편차도 작음(106~123). 쿼리 튜닝으로 얻을 게 거의 없음 |
| **E. 불필요한 revalidation** | 미확인 | F2의 500ms 안에 섞여 있을 수 있음 — **A/D를 걷어낸 뒤 재측정해야 분리 가능** |
| **F. 요청 내 무거운 계산** | 미확인 | 그룹 재계산이 후보. 다만 F1(계산 없음)도 1.17초라 **주범은 아님** |
| **G. 프론트 UX** | **아님** | 화면 반영 **16ms** |
| **H. 기타** | — | 콜드 스타트는 최초 요청에만(+300ms 수준) |

### 결론 한 줄
> **모든 요청에 ~1.1초의 고정 바닥이 깔려 있고, 그 바닥은 쿼리가 아니라 거리(A)다.**
> D·C는 그 위에 얹힌 비용이며, **A를 걷어내기 전에 D·C를 만지면 효과를 측정할 수 없다.**

**따라서 지금은 최적화하지 않습니다.** 순서는 A(리전) → 재측정 → 남은 D·C·E 재분류입니다.

## 5. 고정 IP 서버 — 조사 (만들지 않음)

### 5-1. 현재 구조에서 들어갈 자리
```
브라우저 ──▶ Vercel(서버리스, 고정 IP 없음) ──▶ Supabase(도쿄)
                     │
                     └─(현재 없음) 외부 API: 알리고 / PG / 지오코딩
```
고정 IP 서버가 들어간다면 **Vercel과 Supabase 사이가 아니라, Vercel과 외부 API 사이**입니다.
DB 접근 경로에 서버를 하나 더 끼우면 왕복이 늘어 **A를 악화**시킵니다.

### 5-2. 맡길 수 있는 작업 / 맡기면 안 되는 작업
| 맡길 수 있음 | 이유 |
|---|---|
| 알리고 발송 호출 대행 | IP 화이트리스트를 요구하는 공급사가 많음 |
| PG 웹훅 수신·재시도 | 재시도 7회 같은 흐름은 서버리스보다 상태 유지형이 유리 |
| 배치(그룹 재계산·대량 import) | 요청 타임아웃과 무관하게 돌릴 수 있음 |
| 지오코딩 대량 처리 | 쿼터·백오프 관리가 필요 |

| 맡기면 안 됨 | 이유 |
|---|---|
| 화면 렌더(RSC) | Vercel이 이미 잘하는 일. 옮기면 배포·캐시 이점을 버림 |
| 일반 CRUD | 왕복만 늘어남 |

### 5-3. Supabase와 같은 리전(도쿄)에 둘 때
DB 왕복이 **수 ms 수준**으로 떨어져, 순차 쿼리가 많은 배치에 특히 유리합니다.
다만 **사용자 요청 경로가 아니라 배치·외부 호출 경로**에서만 의미가 있습니다 —
사용자 요청은 어차피 Vercel을 먼저 지나기 때문입니다.

### 5-4. Vercel만 쓰는 것과 비교
| | Vercel만 | + 고정 IP 서버 |
|---|---|---|
| 배포·롤백 | 간단 | 두 곳 관리 |
| 리전 문제 | **설정 하나로 해결 가능(현재 미적용)** | 서버 위치는 자유 |
| 외부 API 화이트리스트 | **불가**(IP 고정 불가) | 가능 |
| 장시간 작업 | 함수 타임아웃 제약 | 자유 |
| 장애 지점 | 1곳 | **2곳** |
| 비용 | 현행 | **추가** |

### 5-5. 비용
소형 상시 인스턴스 1대 수준이면 충분합니다(큐·워커 포함). 다만 **금액은 후보를 정한 뒤
공식 가격표로 확인해야 합니다** — 여기서 임의 숫자를 적지 않겠습니다.
후보 형태: ap-northeast-1에 소형 VM 1대 + 관리형 로그. 트래픽보다 **상시 구동비**가 지배적입니다.

### 5-6. 고정 IP가 **실제로** 필요해지는 시점
```
알리고가 IP 화이트리스트를 요구하는가?      → TRACK A 회신에 달림
PG가 서버 IP 등록을 요구하는가?            → PG 제휴 조건에 달림
```
**둘 다 아직 모릅니다.** 그래서 지금 만들면 **필요 없는 장애 지점이 하나 늘어날 뿐**입니다.

### 5-7. Queue/Worker로의 발전
발전 가능합니다. 구조는 `요청 → 작업 큐 적재 → 워커가 처리 → 결과를 DB에 기록`이고,
**우리 도메인에서 큐가 맞는 작업은 이미 식별돼 있습니다** — 그룹 재계산, 대량 import,
메시지 발송. 특히 메시지는 **F2(Wallet 예약→확정) 구조가 이미 재시도 안전**하게 되어 있어
워커로 옮기기 좋은 형태입니다. 다만 지금 옮길 이유는 없습니다(발송량 0).

### 5-8. 보안·장애 영향
- 서버가 죽으면 **그 서버가 맡은 기능만** 멈춰야 합니다 — 주문·배송은 계속 동작해야 합니다.
  현재 메시지 dispatch가 그렇게 설계돼 있어(실패해도 업무는 진행) 같은 원칙을 적용하면 됩니다.
- `service_role` 키가 **한 곳 더** 존재하게 됩니다 — 유출면이 넓어집니다.
- 외부 노출 포트를 두지 않고 **아웃바운드 전용**으로 두면 공격면을 크게 줄일 수 있습니다.

### 5-9. 권고
> **지금 만들지 않습니다.** 고정 IP의 유일한 확실한 근거(공급사 화이트리스트)가 아직
> 확인되지 않았고, 현재 최대 병목(A)은 **Vercel 리전 설정 하나로 해결 가능**합니다.
> 알리고·PG 회신에서 IP 요구가 확인되면 그때 **외부 호출 대행 + 큐 워커**로 한 번에 만듭니다.
