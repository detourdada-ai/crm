## 1. 사전 확인 — 기존 데이터로 충분했다

지시대로 `error_log`에 실제로 무엇이 저장되는지부터 확인했다.

```ts
interface ImportRowError { row: number; code: ImportErrorCode; reason: string; raw: Record<string, unknown>; }
```

Production 실데이터 조회 결과:

```
[user2] 주문한장_주문템플릿_2026-08-27.xlsx  failed=1  log=1건
   code=missing_contact_info
   reason=[주문번호 없음] 전화번호와 주소가 모두 비어 있어 고객을 식별할 수 없습니다.
   raw키=13개
```

- **`reason`은 이미 사용자용 한글 문장이다.** 내부 스택트레이스가 아니다.
- `code`로 유형 분류도 이미 되어 있다(6종).
- **따라서 새로 만들 것이 없다** → 지시대로 STOP 없이 UI만 구현.

CPO가 화면에서 본 "실패 1"이 바로 위 user2 건이다.

## 2. 구현

실패 건수가 0보다 크고 사유 기록이 있으면, 숫자를 **클릭(또는 PC에서 hover)** 해 팝오버를 연다.

```
실패 3건
연락처·주소 정보 없음 · 2건
같은 주문번호에 다른 고객 정보 · 1건

실패한 행은 등록되지 않았습니다. 엑셀에서 해당 내용을 수정한 뒤
다시 업로드하면 실패한 행만 등록됩니다.
```

- **유형별 집계만** 보여준다. 행마다 주문번호가 섞인 문장을 그대로 나열하면 23줄이 된다
  (실제로 user5 이력이 23건짜리다). 건수 많은 유형이 위로 온다.
- **실패 0건이면 기존 숫자 표시 그대로.** 성공/완료 건에 불필요한 팝오버를 붙이지 않는다.
- 사유 기록이 없는 과거 이력은 실패 건수만 배지로 표시(기존 동작 유지).

### 라벨 매핑
| code | 표시 |
|---|---|
| `missing_contact_info` | 연락처·주소 정보 없음 |
| `missing_order_number` | 주문번호 없음 |
| `order_number_conflict` | 주문번호 충돌 |
| `identity_conflict` | 같은 주문번호에 다른 고객 정보 |
| `repeat_confirm_needed` | 같은 주문번호 반복 — 확인 필요 |
| `processing_error` | 처리 중 오류 |

> `missing_contact_info`를 CPO 예시의 "연락처 정보 없음"으로 줄이지 않았다. 이 코드는
> **전화번호와 주소가 둘 다 비었을 때만** 나오는데, 연락처만 언급하면 주소가 있어도
> 실패한 것처럼 읽혀 **사장님이 엉뚱한 칸을 고치게 된다.**

## 3. 개인정보 — `raw`를 브라우저로 보내지 않는다

`error_log.raw`에는 업로드 원본 행이 통째로 들어 있다(실측 13개 컬럼 = 고객 이름·연락처·주소).
**실패 사유를 보여주려다 목록 화면이 개인정보 노출 지점이 되면 개선이 아니라 사고다.**

그래서 집계를 **서버(테이블 컴포넌트)에서 끝내고** 클라이언트 컴포넌트에는 `{label, count}`만
넘긴다 — `raw`는 RSC 페이로드에도 실리지 않는다. E2E가 이를 직접 검증한다(T8~T10).

## 4. UX — PC hover / 모바일 클릭

CPO 지시대로 **클릭이 기본**이다(모든 기기에서 동작). PC에서는 hover도 추가로 열린다.

터치 기기에서 `mouseenter`가 탭과 겹쳐 열자마자 닫히는 문제가 있어, `(hover: hover) and
(pointer: fine)` 미디어 쿼리로 **실제 마우스가 있는 기기에서만** hover를 켠다. 트리거에서
팝오버로 마우스를 옮기는 동안 닫히지 않도록 닫힘을 120ms 늦춘다.
