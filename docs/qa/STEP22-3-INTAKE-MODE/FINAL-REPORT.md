## 1. 구현 내용

### UI — 라디오 2개 + 날짜 1개
`가져올 주문 범위` **위에** `접수 방식`을 추가했다. 기존 컨트롤의 의미는 건드리지 않았다.

```
접수 방식
  ● 누적 등록                    ← 항상 기본값
  ○ 당일 배송 최신화
    └ 최신화할 배송일 [ YYYY-MM-DD ]  + 경고 배너
```

**접수 방식은 계정에 저장하지 않는다.** 매번 `누적 등록`에서 시작한다.
잘못 기억되면 사장님이 인지하지 못한 채 매번 기존 배송 대상이 제외되기 때문이다(CPO 확정).

### 처리 — 전부 `order_shipments` 단위

```
최신화 대상 = order_shipments
  WHERE tenant_id = 내 사업장
    AND delivery_date = 선택한 배송일
    AND delivery_status NOT IN ('완료','취소')
    AND 부모 orders.import_id IS NOT NULL
```

"파일에 있음"은 **그 배송건의 상품주문번호가 이번 파일에 등장하는지**로 본다 —
배송일이 바뀐 건도 유지된다. 파일에 없는 배송건만 `cancelMany`로 제외한다.

**취소 계산은 등록이 끝난 뒤에 한다.** 이번 파일로 새로 생긴 배송건이 제외 대상에
잘못 걸리면 안 되기 때문이다. 그리고 브라우저가 보낸 미리보기 숫자를 믿지 않고
**확정 시점에 서버가 다시 계산한다**(기존 중복판정과 같은 원칙).

### 안전장치 3가지
1. 확정 전 **제외 예정 건수** 표시
2. **파일에 그 배송일 주문이 0건이면 확정 버튼 비활성** + 사유 표시
3. 배송중 누락 건은 **"자동 취소하지 않습니다. 확인이 필요합니다."** 로만 표시

```
Case2    확정 전 '제외 예정' 표시 / 배송중 확인 필요 안내 표시
Case2    파일에 있는 건 유지 · 신규 등록 · 누락 건 취소
Case3/8  미래 배송일(D1) 건 무변경
Case9 ★  같은 주문의 다른 배송일 건(MULTI-B) 취소되지 않음
Case9    같은 주문의 당일 건(MULTI-A)은 파일에 있어 유지
Case4    배송중 자동 취소 안 됨 (배송중 유지)
Case5    배송완료 자동 취소 안 됨 (완료 유지)
Case6    수기 주문 무변경
Case10   타 테넌트의 같은 배송일 배송건 무변경
Case11 ★ DELETE 0 — 주문 7→8 / 배송건 8→9 (증가만, 감소 없음)
```

**Case9가 이번 구현의 핵심 검증이다.** 같은 주문번호에 D0·D1 두 배송일이 걸린 주문을
만들어, D0 최신화가 D1 배송분을 건드리지 않는 것을 확인했다. `orders` 단위로 판단했다면
이 케이스에서 D1까지 취소됐을 것이다.
