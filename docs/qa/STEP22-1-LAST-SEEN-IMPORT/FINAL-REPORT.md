## 2. 여러 import 사이에서 데이터가 어떻게 변하는가

|---|---|---|---|---|
| A | import1 | import1b | **import2** | import2 (유지) |
| B | import1 | import1b | import1b (유지) | import1b (유지) |

- 주문/배송/상태는 **어느 경우에도 바뀌지 않았다.**

## 5. ★ 2단계에서 정상 주문을 잘못 취소할 가능성 — 세 갈래로 정리

이번 단계의 결과물을 2단계에서 잘못 쓰면 대량 오취소가 난다. 확인된 위험은 셋이다.

### ① `null`을 "사라졌다"로 읽으면 안 된다
`last_seen_import_id`가 null인 경우는 **"파일에서 사라졌다"가 아니라 "모른다"** 다.
- 이 기능 이전에 등록된 건 (현재 **user1 0건 / user2 0건** — 백필하지 않았으므로 기존 전부 null)
- 해당 import가 **30일 보관기간 만료로 파기**된 경우(FK `on delete set null`)

> **2단계 판정 조건은 반드시**
> `last_seen_import_id IS NOT NULL AND last_seen_import_id != 이번 import`
> 여야 한다. null을 포함시키면 **기존 주문 전체가 즉시 취소 대상이 된다.**

마이그레이션 주석과 `OrderItem` 타입 주석 양쪽에 못박아 두었다.

### ② 파일이 커버하지 않은 구간을 비교하면 안 된다
실측한 실제 파일의 주문일 범위는 매번 다르다(13일 / 9일 / 10일). 기간 한정 없이
비교하면 9/4→9/7에서만 **정상 주문 61건이 오탐 취소**된다. 4번의 방법으로 구간을 한정해야 한다.

### ③ 날짜 필터로 걸러진 행도 "파일에 있었다"로 취급했다 (이번 단계에서 이미 반영)
'오늘만 등록' 모드로 올리면 파일에는 있지만 이번에 처리되지 않는 행이 생긴다.
그 행에도 도장을 찍도록 구현했다 — 빼면 **그 날 과거 주문이 전부 사라진 것으로 보여**
2단계에서 대량 오취소가 난다.
