# P2 — 배송관리 "변경사항 저장" 고정비 계측 보고

> 2026-09-04 / CTO. **계측까지만** 수행하고 최적화는 하지 않았다(CPO 지시: 추측으로 리팩터링 금지).
> 재현: `scripts/qa/perf-save-cost-breakdown.ts` (Production 대상, user3, finally에서 baseline 복귀)

## 1. 계측 설계

제품 코드에는 계측 코드를 넣지 않았다. 브라우저가 실제로 주고받은 요청의
타이밍(Playwright `request.timing()`)만 읽어 저장 1회를 네 구간으로 쪼갠다.

| 구간 | 정의 |
|---|---|
| 전송 | 저장 클릭 → 요청 첫 바이트 전송(클라이언트 직렬화) |
| 서버 | `requestStart → responseStart` (액션 실행 + 첫 응답까지) |
| 다운로드 | `responseStart → responseEnd` (revalidate 후 RSC 페이로드 수신) |
| 화면 | 응답 완료 → "저장했습니다" 토스트 표시(클라이언트 재렌더) |

두 축으로 나눠 **건수 비례분**과 **보드 크기 영향**을 분리했다.
- A: 보드 N건 전체 선택 → 일괄 적용 → 저장 (N = 1/10/50/100/150)
- B: 보드 150건에서 **1건만** 변경해 저장

## 2. Production 실측 (median, 5회)

| 케이스 | 전송 | 서버 | 다운로드 | 화면 | 합계 |
|---|---:|---:|---:|---:|---:|
| A 보드1 / 변경1 | 24ms | **2,029ms** | 974ms | 14ms | 3,041ms |
| A 보드100 / 변경100 | 129ms | 2,176ms | 1,245ms | 43ms | 3,597ms |
| A 보드150 / 변경150 | 190ms | 2,132ms | 1,268ms | 54ms | 3,698ms |
| B 보드150 / 변경1 | 191ms | **2,269ms** | 1,179ms | 55ms | 3,717ms |

> A 10건/50건 행은 저장 액션이 아닌 다른 next-action POST를 먼저 잡은 표본이 섞여
> median이 오염됐다(합계는 2.6~2.8초로 동일 대역). 결론에는 쓰지 않았다.

**확정된 사실**
1. 체감 3~3.7초 중 **95%가 서버 구간(서버 2.0~2.3초 + 다운로드 1.0~1.3초)** 이다.
2. 클라이언트 렌더는 **14~55ms** — 화면이 무거워서 느린 것이 아니다.
3. 변경 건수 비례분은 **전송 24→190ms** 뿐이다. 1건을 저장해도 150건과 거의 같은 시간이 든다.
4. 보드 150건 / 변경 1건(B)이 보드 1건 / 변경 1건(A)보다 느리지 않다 → **목록 크기도 원인이 아니다.**

## 3. 고정비의 위치 — 동일 코드 / 동일 DB 대조군

같은 커밋을 로컬에서 `next build && next start`로 띄우고, **같은 Supabase(Production DB)** 를
바라보게 한 뒤 같은 스크립트로 측정했다.

| 케이스 | Production 서버구간 | 로컬 서버구간 | 차이 |
|---|---:|---:|---:|
| A 보드1 / 변경1 | 2,029ms | **603ms** | −1,426ms |
| A 보드150 / 변경150 | 2,132ms | 722ms | −1,410ms |
| B 보드150 / 변경1 | 2,269ms | 767ms | −1,502ms |
| 합계(체감) | 3,041~3,717ms | 1,123~1,808ms | 약 −1.9초 |

DB가 동일하므로 **쿼리 자체가 느린 것이 아니다.** 실행 환경 차이다.

DB를 전혀 쓰지 않는 함수 경로(`/api/import/template`, 세션검증+엑셀생성)로 플랫폼 왕복만 재면:

| | Production | 로컬 |
|---|---:|---:|
| `/api/import/template` TTFB | 1,203ms(첫 요청) → **360~368ms**(warm) | 7~39ms |
| `/delivery` TTFB (빈 보드) | 1,058ms | 605ms |

- 플랫폼 왕복 고정비 = 약 **360ms**.
- 저장 액션의 Production↔로컬 차이 **약 1,430ms** 중 360ms만 왕복으로 설명되고, **나머지 약 1,070ms가 남는다.**
- 한편 `/delivery` 페이지(조회 쿼리를 `Promise.all`로 **병렬** 실행)의 차이는 450ms로 훨씬 작다.
- 저장 액션은 `requireSession → findByIds → deliveryGroups.findByIds → findByGroupIds → 쓰기`로
  **최소 5회 순차 왕복**한다(`src/actions/delivery.ts:421-591`).

즉 관측된 값은 **"왕복 1회 지연 × 순차 왕복 횟수"** 로 일관되게 설명된다.
응답 헤더 `X-Vercel-Id: icn1::iad1::…` — 진입은 서울 엣지지만 **함수 실행은 iad1(미국 동부)** 이다.

## 4. 결론 (측정으로 확인된 범위)

- 고정비는 **클라이언트도, 목록 크기도, 변경 건수도 아니다. 서버 구간이다.**
- 서버 구간은 ① 플랫폼 왕복 약 0.36초 ② 액션 내부의 **순차 DB 왕복 누적**(약 1.1초 추정분)
  ③ revalidate 후 RSC 재렌더 스트리밍 1.0~1.3초로 구성된다.
- ①②는 **함수 실행 리전과 DB 사이의 거리**에 비례한다. 같은 코드가 로컬에서 3배 빠른 이유가 여기 있다.

## 4-1. 실행 경로 확정 (2026-09-05 추가 조사)

추정이던 "리전 간 거리"를 실제로 확인했다.

| 항목 | 확인값 | 근거 |
|---|---|---|
| 함수 실행 리전 | **iad1(미국 버지니아)** | 동적 경로 응답의 `X-Vercel-Id: icn1::iad1::…`(`/`, `/login` 반복) |
| Supabase DB 리전 | **AWS ap-northeast-1(도쿄)** | `db.<ref>.supabase.co` → `2406:da14:…`, AWS `ip-ranges.json`의 `2406:da14::/35` = ap-northeast-1 |

즉 현재 경로는 `사용자 → 서울 Edge → 함수(버지니아) → DB(도쿄)`이고, 저장 액션은 그 사이를
**순차로 5회 이상 왕복**한다. 태평양 왕복 150~180ms × 5회 + 플랫폼 왕복 0.36초가 측정된
서버 구간 2.0~2.3초와 일치한다.

저장소에는 `regions`/`preferredRegion` 설정이 없어 **Vercel 프로젝트 기본 리전**이 적용 중이다.
변경 수단은 ① 프로젝트 설정의 Function Region(코드 변경 0, 계정 소유자 권한 필요)
② `vercel.json`의 `regions`(다중 리전은 Pro 이상) ③ route별 `preferredRegion`(제품 코드 변경).

## 5. 개선 후보 (CPO 결정 사항 — 실행하지 않음)

| 안 | 내용 | 예상 효과 | 리스크 |
|---|---|---|---|
| A | Vercel 함수 실행 리전을 DB에 가까운 곳(예: `icn1`)으로 이동 | 저장·조회 **모든 요청**에 즉효, 코드 변경 0 | 배포 설정 변경 / 플랜 제약 / 해외 사용자 영향 확인 필요 |
| B | 저장 액션의 순차 조회 3회를 병렬·통합(RPC 1회)으로 축소 | 액션당 왕복 2~3회 절감 | 그룹 override 판정 로직 변경 — 회귀 위험 있음, 게이트 필수 |
| C | `revalidatePath` 3경로(`/delivery`·`/orders`·`/driver`) 축소 | 다운로드 1.0~1.3초 구간 단축 가능성 | 다른 화면 최신성 저하 — 정책 판단 필요 |

**추천 순서: A → 재측정 → (남으면) C → B.** A는 코드 변경이 없어 되돌리기 쉽고 효과 범위가 가장 넓다.
B는 STEP12-8B/8F에서 여러 번 회귀가 났던 지점이라 마지막에 손대는 것이 맞다.

## 6. 리전 변경 후 재측정 절차 (CPO 확정, 2026-09-05)

**첫 실험은 `hnd1`(도쿄).** 사용자 위치보다 먼저 `함수 ↔ DB` 왕복을 제거하는 것이
가장 깨끗한 원인 검증이기 때문이다(서울로 가면 도쿄 DB 왕복이 그대로 남는다).

변경 후 **새 스크립트를 만들거나 조건을 바꾸지 않는다.** 아래 그대로 재실행한다.

```bash
NODE_OPTIONS="--conditions=react-server" npx tsx -r dotenv/config   scripts/qa/perf-save-cost-breakdown.ts dotenv_config_path=.env.local 5
```

동일 Production · 동일 DB · 동일 QA 데이터 조건 · 최소 5회 · **median 비교** · baseline diff = 0 유지.

| 비교 시나리오 | 변경 전 기준(median) |
|---|---:|
| A 보드1 / 변경1 — 서버 구간 | 2,029ms |
| A 보드150 / 변경150 — 서버 구간 | 2,132ms |
| B 보드150 / 변경1 — 서버 구간 | 2,269ms |
| 전체 체감 | 3.0~3.7초 |

**기대값(“몇 ms면 PASS”)은 미리 정하지 않는다.** 결과를 보고 판단한다.
조사에서 hnd1이 유력하다고 봤지만 그것은 가설일 뿐이며, **예상 개선폭을 미리
말하거나 전제하지 않는다**(CPO 정정, 2026-09-05). 판단 근거는 실측값뿐이다.

1. 큰 폭 개선 → 개선안 A 확정
2. 일부 개선 → 남은 비용을 다시 구간 분해
3. 개선 미미 → 리전 외 원인 재조사(순차 왕복 수·revalidate 경로)
